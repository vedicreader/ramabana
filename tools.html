tools

Hosts, tool lists and sub-agents: what Ramabana adds on top of the shalya toolset.

A model can only write text. To read a file or run a command it calls a tool: a Python function whose name, docstring and typed parameters the backend turns into a schema the model sees. Ramabana’s tools come from shalya.

The tools act through a host. A host is the object that decides which folders are open (its roots), whether files may be written, and which other services exist, such as a shell, a Python kernel, git or the web. Each such service is a capability group. A host declares a group by inheriting the class that names it, such as CodeHost or WebHost, and Host.provides lists the groups it declares. Every host has the file group. The tools that need one capability group form a tool group: the shell group, for example, is run_shell, run_shell_bg, shell_output and shell_stop.

Shalya holds the host classes, the functions that build each tool group, the conventions tool results follow (err writes a failure that failed recognises), and the skills registry. This module re-exports all of them, so code that imports them from ramabana.tools keeps working, and Leela’s sys.modules[__name__] = ramabana.tools alias keeps resolving. New code imports them from shalya.

What this module adds needs parts of the agent that a toolset should not know about. A sub-agent needs a Backend to talk to and a Run to record it, and draws_itself needs a ModelSpec. The sections below cover a host that refuses everything, the image tools, tools_for, which builds the tool list a turn gets, delegation to sub-agents, and attachments.

A host with nothing behind it

NullHost is a host with no folders and no services. Checking a path raises HostError, reading returns nothing, and writing or deleting raises. It declares no capability group beyond file, and because its writes is False, tools_for gives it view_file and nothing else. Use it in a test, or wherever code needs a host object that must not touch the disk. The examples under it, and two further down, show each refusal.

Drawing

Shalya’s generate_image tool makes pictures. Some models can draw themselves when they are given the image tool. For any other model the prompt goes to a separate image model. Which case applies is a fact about the turn’s model, so shalya asks for it as a callable, and this module supplies the callable.

draws_itself looks up a model’s capabilities with spec_caps and returns True when image is among the tools the model supports (Caps.tools). The supported_output_modalities field cannot answer this: it says no for every chat model, because it describes what a model returns without being asked.

Assembling the tool list

tools_for decides which tools a host gets. It asks Host.provides for the capability groups and adds the tool group for each. A get_skills callable adds read_skill, and extra adds extension tools. drop removes groups by name, such as 'shell' or 'image'. optin adds groups that are off by default: exhash (the hash-addressed edit_file), research, author, legacy (tool names from older releases) and browser.

Shalya has a tools_for of its own. Use this one in Ramabana code, because it also builds the image group from the turn’s model through get_spec and on_media, which a host cannot know. The image group comes only when an image key is set and the host can write, since generate_image saves files. On a LocalHost without litesearch installed, search_code is left out.

small_tool marks an extension tool to keep in the small profile, the short catalog a local model or a small context window gets. ToolCatalog wraps a tool list once and answers questions about it: each tool’s group, which tools write, which have effects, and a read-only copy. ToolEntry is one row of it.

Sub-agents

A sub-agent is a separate conversation with a model, started to answer one question for the agent that asked. Handing a question over this way is delegation. Its purpose is to save context, not time. A broad question can take twenty tool calls to answer, and if the main agent made them itself every result would stay in its conversation. Delegated, the same work costs the main conversation one question and one answer, because the sub-agent’s conversation is thrown away when it finishes.

A sub-agent gets read-only tools unless the session allows it to write. NO_SUB lists the tools it never gets by default: the four delegation tools and the folder watches, which would outlive its task. A session that allows nesting passes its own block, and then the sub-agent may delegate in turn. SUB_MAX_STEPS, SUB_TIMEOUT and SUB_SLOTS are the default step limit, the default time limit, and how many sub-agents may work at once.

A briefing is the standing instructions a model gets before the conversation starts, its system prompt. sub_briefing builds a sub-agent’s from parts: SUB_SP_HEAD, which every sub-agent gets, then SUB_READ_SP or SUB_WRITE_SP, then an optional note on how much of the answer the caller will read, then notes for the model’s family.

read_only, from shalya, filters a tool list down to what an agent may have when it must not change anything. Write tools are dropped, or swapped for a safe version where the tool has one. block drops tools by name, and Ramabana passes NO_SUB. effects=False also drops the acting tools, those that do something without writing a file, such as inspect_python, shell_stop and generate_image. Shalya marks them with acts and lists them in ACTING_TOOLS. Use effects=False for a surface that may look and propose but never act.

A safe version can fix an argument. In the second cell below, read_url still fetches the page, but its remember parameter is gone and it no longer stores the page in the vault.

max_calls puts a hard budget on the list. Past it, every tool returns a message telling the model to stop and answer. Local engines run their own tool loop, so Ramabana cannot stop them between steps, and a budget inside the tools is the one limit that works on every backend. Below, the second search is refused.

budgeted = read_only(ts, max_calls=1, block=NO_SUB)
search = next(t for t in budgeted if t.__name__ == 'search_code')
search('return'), search('return')

delegate asks one question of a sub-agent. It spawns a new conversation on the same engine as backend, hands it the tools that read_only lets through (all of them with writes=True), sends the question, and closes the conversation in a finally block whether or not it succeeded. It returns the answer text. An empty or repetitive answer is replaced by a notice that the delegation failed, and a sub-agent that raised gives an error result. timeout cancels the run after that many seconds, and slots, a shared Slots, makes it wait for a free place among the sub-agents working at once. A sub-agent waiting on sub-agents of its own lends its place back, so a full tree of delegations cannot deadlock.

Use delegate for one question. delegate_many, below, asks several, and subagent_tools wraps both as tools a model can call.

A sub-agent’s briefing: standing instructions, then the bodies of skills its task named.

The tools a sub-agent gets are wrapped. A message sent to a running sub-agent, with /tell in the terminal, arrives appended to its next tool result inside a <user-message> tag that carries the run’s key. inbox_note tells the sub-agent that only a tag with that key is the user speaking, since a file or a web page could contain the same tag. A sub-agent that gets the same result from the same call REPEAT_CALLS times in a row is told to change course. The cell below shows a queued message arriving with a result.

Each wrapped call also marks the run as active, so the now pane, the side panel that lists live runs (see pane), can show what a sub-agent is doing. Some backends, LiteRT for one, never pass on the text a model writes between calls. Their sub-agents get a status tool from status_tool to report one line instead, and STATUS_NOTE in the briefing tells them to use it.

delegate_many asks several questions at once, one sub-agent each, and returns the answers in the order the questions were asked. It registers every child run with the parent before any starts, so cancelling the parent reaches all of them; the last example on this page shows that. It runs the questions one at a time when sub-agents may write, and when the model is local, because an engine such as LiteRT holds one conversation at a time and parallel runs would race for it.

delegate_many(be, ['what imports fastllm?', 'where is compaction triggered?'], tools=ts)

The delegation tools take callables that return a backend, not a backend. Each call asks for the current session’s backend, so after a /model switch the next sub-agent runs on the new model.

delegate_async starts a sub-agent in the background and returns at once, so the turn can carry on while it works. Background keeps track of those runs. start registers a run before its thread begins, so a status call always finds the id it returned. At most mx runs reach a model at once (ASYNC_MAX, 4 by default) and the rest wait as pending. status, result and cancel answer for one run, and status with no id answers for all. The last keep answers are held. close, called when the session ends, cancels every run and refuses new work.

The examples hold two runs behind a register with one place, cancel a run still waiting, close a register, catch a run that raised, and show an answer dropped once newer ones push it out.

subagent_tools builds the four tools a model uses to delegate. delegate_search asks one or more questions and waits for the answers. delegate_async starts one question in the background and returns a run id. delegate_result collects a background answer, or with no id lists every background run, and delegate_cancel stops one. Every argument is a callable read on each call, so the backend, the step budget, the time limit and the write setting follow the session as they change. An answer longer than one tool result may be is cut, and the whole text is saved to a file whose path the cut answer names.

delegate_many registers every child run before any work starts. Cancelling the parent stops the child that is running, and the children still queued never spawn. The fake backend below blocks on its first question until it is cancelled.

class _Sub:
    max_steps = 0
    def __init__(self, owner): self.owner, self.release = owner, threading.Event()
    def send(self, question, run=None):
        self.owner.started.append(question); self.release.wait(); return 'late'
    def cancel(self): self.owner.cancelled += 1; self.release.set(); return True
    def close(self): pass

Attachments

A prompt can carry files: pictures and sound. These helpers live here rather than in the terminal module, so that a host that only sends files does not load the terminal UI. media_paths reads a paste or a dropped file in the shapes terminals deliver it, quoted, backslash-escaped or as a file:// URL, and returns the media files it names, or an empty list for any other text. attach_refs finds @path references in a prompt. clipboard_png reads a picture from the clipboard with pngpaste, wl-paste or xclip, whichever is installed. Attachment holds one file’s bytes, read once. media_parts and media_note turn a list of attachments into what the message sends: the bytes the model accepts, and a note listing every file. Audio goes to the model only when it accepts audio; otherwise the note gives the file’s path.
