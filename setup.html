setup

The first run: ramabana starts inside its own tmux server, offers to install tmux when it is missing, and ramabana --doctor says what it found.

This module holds what must happen before a session starts. The terminal session runs best inside tmux, a terminal multiplexer that divides one window into panes. tmux gives Ramabana a split for the now pane, the live view of the turn described in pane. With the extended keys setting on, tmux also delivers the alt keys and shift+enter to the program as keys of their own. shift+enter arrives only from a terminal that sends it. The first run therefore starts Ramabana inside a tmux server of its own and offers to install tmux when it is missing. ramabana --doctor reports what it found. The module also decides whether the code index needs rebuilding.

Extras and scripts

Every console script that the package installs starts in this module. The module imports only fastcore and the standard library, and never ramabana.core. A script starts quickly this way and can check for its dependencies before it imports them.

installed(mod) says whether a module would import, without importing it. need(extra) checks the modules of an extra, as listed in EXTRAS. It returns '' when all are installed. Otherwise it returns a message that names the missing modules and gives the pip install command. SCRIPTS names each console script other than ramabana, with the module whose main it runs, the extra it needs and the modules it needs. A lookup of one of these names on this module returns that main. When a needed module is missing, the lookup returns a stand-in that prints the message and exits with status 2. follow_cmd(log, snap) is the shell line a transcript pane runs: the pane module following log in the palette of the snapshot snap, or tail -f when the terminal extra is missing. ramabana.core re-exports installed, need, EXTRAS and SCRIPTS.

The config

Each session gets a tmux server of its own, started as tmux -L ramabana-<id> with the config file <cfg>/tmux.conf. A new server reads the current tmux.conf and inherits the current environment. A second session therefore never picks up the first one’s API keys or virtual environment. That server never reads ~/.tmux.conf. Your own tmux setup stays as it was.

Extended keys are a tmux setting that passes key combinations such as shift+enter through to the program in the pane. Without it, tmux folds them into plain enter. tmux_conf(version) returns the config for a tmux version. It adds only the lines that version understands. An older tmux prints an error for each line it does not know. tmux_version reads the version from the output of tmux -V. The config claims true colour (RGB) only when $COLORTERM says the terminal draws it. The cell below prints the config for tmux 3.5.

3.0 WRAP_MIN launch relaunches inside tmux
3.1 SPLIT_MIN The split for the now pane
3.2 KEYS_MIN extended-keys
3.5 none extended-keys-format csi-u

The relaunch

Setup collects everything about the tmux that Ramabana runs in: the config, the relaunch into it, the install offer and --doctor.

Setup.launch runs before an interactive session starts. Outside tmux it replaces the current process with tmux new-session on a new server. The new session runs the same command line in the same folder. Quitting Ramabana then ends that tmux session and returns you to your shell. launch does nothing in these cases: a one-shot prompt, --json, a stdin or stdout that is not a terminal, and --tmux off or $RAMABANA_TMUX=off. It also does nothing when $RAMABANA_WRAPPED is set, when tmux is older than 3.0, and when tmux is missing and you decline the install offer. The relaunched process has $RAMABANA_WRAPPED set. It never relaunches a second time. Inside tmux, --pane auto then opens the now pane.

The server sets destroy-unattached, which ends the session when you detach or close the window. Ramabana never keeps running where nobody can see it. The history is saved, and --resume latest reopens it. The command runs under sh with a short wrapper, HOLD. After a non-zero exit, HOLD waits for enter. An error stays on screen instead of vanishing with the tmux session. The command line is in the tmux arguments, so the tmux client’s argv holds the full ramabana command line. HOLD starts with set -m, which turns on job control in sh. The command then runs in its own process group, and that group owns the pane’s terminal. A tool that finds the program in front of a terminal by its process group, such as Sanketa, then finds ramabana and not sh. After the command exits, sh takes the terminal back for the wait. sh turns job control on only when it has a terminal. A tmux pane always gives one, so the example below runs HOLD in a terminal of its own.

Inside a tmux server of your own, launch turns extended-keys on for that server when it is off. The change lasts until the server exits. Only programs that ask for extended keys receive them.

Every effect on the outside world goes through an argument of Setup: which, system, run, execvpe, ask and isatty, plus environ, argv and cwd. The examples pass fakes for all of them. They run without tmux and change nothing.

from types import SimpleNamespace
import tempfile

class Box:
    "Programs on PATH, the commands run, the prompts shown and the exec made."
    def __init__(self, have=('tmux',), version='tmux 3.5a', system='Darwin', answer='', ext='on'):
        self.have, self.version, self.system, self.answer, self.ext = set(have), version, system, answer, ext
        self.calls, self.asked, self.execd = [], [], None
    def which(self, name): return f'/bin/{name}' if name in self.have else None
    def run(self, cmd, **kw):
        self.calls.append(list(cmd))
        if 'install' in cmd: self.have.add('tmux')
        return SimpleNamespace(returncode=0, stdout={'-V': self.version, 'show': self.ext}.get(cmd[1], ''))
    def ask(self, q): return self.asked.append(q) or self.answer
    def execvpe(self, *a): self.execd = a

Each relaunch starts a tmux server on a new socket. A tmux server leaves its socket file behind when it exits, even after tmux kill-server. launch calls prune_sockets before each relaunch. prune_sockets removes each ramabana- socket that refuses a connection, because no server listens on it. It keeps live sockets and the sockets of other programs. It also keeps a socket younger than age seconds, because a server that is still starting refuses connections for a moment. An error on one socket skips that socket and does not stop the launch. The example binds one live socket and two dead sockets in a temporary folder. The new dead socket stays until age=0:

import socket
d = Path(tempfile.mkdtemp(dir='/tmp'))
socks = {n: socket.socket(socket.AF_UNIX) for n in ('ramabana-live', 'ramabana-dead', 'mine')}
for n, s in socks.items(): s.bind(str(d/n))
socks['ramabana-live'].listen()
for n in ('ramabana-dead', 'mine'): socks[n].close()
test_eq(prune_sockets(d), [])
test_eq(prune_sockets(d, age=0), ['ramabana-dead'])
socks['ramabana-live'].close()
left = sorted(p.name for p in d.ls())
shutil.rmtree(d)

The ramabana script, run_cli, makes the tmux decision before it imports the CLI. Importing the CLI takes about 0.4 seconds. Deciding first lets the process outside tmux hand over to tmux quickly. launch_args(argv) reads just enough of the command line to know the session is interactive, without the full option parser. It returns the cfg and tmux values that launch needs. It returns None to leave the decision to main in the CLI. It returns None for a prompt, for any option in EARLY (such as --json, --doctor and --help), for --tmux off, for a valued option with no value, and for options that refusal rejects. An option it does not know is skipped.

refusal holds the checks that main makes before it starts anything, such as --pii without --vault. It returns the reason or ''. Running it in run_cli refuses a bad option in your terminal and not on the tmux hold screen. bare_resume gives a bare --resume the value PICK_SESSION, which lists this folder’s sessions to choose from. When run_cli has called launch, it sets LAUNCHED. main then does not call launch again.

config.toml

~/.config/ramabana/config.toml holds this machine’s settings: one file, edited by hand, that every Ramabana on the machine reads. A session started with another --cfg, and an app that embeds Ramabana with a config folder of its own, read the same file and never write into their own folder for it. $RAMABANA_CONFIG names another file; the tests use it.

A value can come from four places, and the first that has one wins:

Source Example
a command-line flag --model gpt-5.4
an env var $RAMABANA_MODEL, or $LEELA_MODEL inside Leela, the notebook editor that embeds Ramabana
config.toml [jobs] turn = "gpt-5.4"
the built-in default claude-opus-5-5

KEYS lists every key: its type, the env var and the flag that beat it, what it sets, and the values it may take. drop_tools, at the top level, names the tools a session leaves out of the model’s schema. Each tool’s schema costs tokens on every call. With no drop_tools, a session keeps every tool. The tables are [jobs], the model each job runs on; [window], the numbers the window guard works with; [compaction]; [runtime], what a model is started with; and [cli], the defaults of the terminal session’s flags that take a value. [jobs] image is the OpenAI-compatible model generate_image draws with. [azure] holds Azure OpenAI’s endpoint, which $AZURE_OPENAI_ENDPOINT beats, read as named with no prefix (Key.plain), and the api_key_env that names the env var holding its key. A key an earlier release read, such as azure.deployments, is reported with what to do instead (RETIRED_KEYS). A [model."NAME"] table corrects the numbers fastllm’s table gives one model: max_input_tokens, max_output_tokens and supports_images. Given model_id, the same table defines a model of that name, with runtime, base_url, api_key_env, api_name, vendor_name and ctx; core registers it.

load_config reads the file again only when it changes. An entry it cannot use takes its default and gives one warning, which Agent.problems and ramabana config show repeat: a key nobody knows, with the nearest one it might mean; a value of the wrong type or outside its choices; a file that is not TOML. Nothing raises.

keys.env, beside config.toml, stores API keys saved by /login. A name already in the environment wins over the file. The CLI loads keys.env before any subcommand. The beat loads beat.env first and keys.env second. A name in beat.env therefore wins in the beat.

A value beginning with ! runs a shell command and uses its stripped output, for example OPENAI_API_KEY=!security find-generic-password -ws openai on macOS, or OPENAI_API_KEY=!op read op://vault/item/key. A command that fails, prints nothing or runs longer than 30 seconds leaves that name unset and prints a warning on stderr. To store a value that begins with a literal !, prefix it with $: $!text loads as !text.

Only the owner may read the file (chmod 600). load_keys refuses a file that other users can read and prints a warning on stderr. Saved values are never printed or logged.

A vesha is a named composition in vesha/NAME.toml beside config.toml: config keys, an optional extends naming a vesha applied first, and an optional mods allow list. load_vesha follows the chain and records which vesha set each key, which config show names as the source. An unknown name, a cycle or a key config.toml does not know raises ValueError with the valid names:

vd = Path(tempfile.mkdtemp())
(vd/'base.toml').write_text('[jobs]\nturn = "gpt-5.4-mini"\n')
(vd/'deep.toml').write_text('extends = "base"\nmods = ["pomodoro"]\n\n[cli]\nhints = false\n')
deep = load_vesha('deep', vd)
test_eq(deep.sources, {'jobs.turn': 'base', 'cli.hints': 'deep'})
test_fail(lambda: load_vesha('nope', vd), contains='base, deep')
deep

A vesha may tighten a permission but never loosen it. PERMISSIONS names the keys that set what a session may do, cli.approve, cli.pii, cli.read_outside and cli.vault, each with its values from strictest to loosest. run_cli holds each one a vesha sets against the built-in default under config.toml, and loosened names the first that is looser, so start-up stops instead of quietly granting more. A flag on the command line still wins, which makes --approve auto the way to loosen one session:

(vd/'eager.toml').write_text('extends = "deep"\n\n[cli]\napprove = "auto"\n')
built_in = {'cli.approve': 'ask', 'cli.pii': PII_OFF, 'cli.read_outside': False, 'cli.vault': False}
test_eq(loosened(load_vesha('deep', vd), built_in), '')
test_eq(loosened(load_vesha('eager', vd), built_in, skip={'cli.approve'}), '')
loosened(load_vesha('eager', vd), built_in)

Installing tmux

When tmux is missing, offer_install shows the install command and asks once whether to run it. The command is brew install tmux on macOS, and sudo apt-get install -y tmux or sudo dnf install -y tmux on Linux. installer picks the command from what is on PATH. The command runs attached to the terminal. sudo can therefore ask for a password.

offer_install stores the answer in <cfg>/setup.json. It never asks again after a no, after a yes whose install worked, or when no install command exists. Without tmux, the session starts in the current terminal and prints one line on how to get the now pane.

Whether the code index needs to run

The search_code tool searches a code index that kosha builds over the installed packages and the open folders. Rebuilding the index is called a sync. A sync takes time. The session skips it when nothing the sync reads has changed.

index_gate(cfg, roots) decides this without importing kosha. index_state takes a fingerprint of what a sync would read. The fingerprint holds the installed distributions that importlib.metadata finds, with their modification times (pkg_state). For each folder it holds the git HEAD and a digest of git status with the modification times of the paths it names (root_state). Outside git, a folder’s fingerprint hashes each visible file’s relative path, size and nanosecond modification time, skipping hidden files and folders. index_gate returns the fingerprint and a reason to run kosha, or '' to skip the sync. The reason is '' when the fingerprint matches the one that the last good sync saved in <cfg>/kosha-state.json, and each folder’s .kosha/code.db and kosha’s package database, kosha_env_db(), exist. When the fingerprint matches and a database is missing, the reason is index missing. Otherwise index_changes says what changed, such as packages changed: +foo 1.2.

After a good sync the session calls save_index to store the new fingerprint. Either way log_index appends one line to <cfg>/kosha.log, and --doctor shows the last line through last_index. The example walks a fresh folder through a first sync, a missing index, an unchanged state and a new package:

Peer hooks

ramabana setup peers puts the peer hooks of peer_hooks and the peer-work text of peer_work into the config of Claude Code and Codex, so those sessions can talk to each other and to Ramabana. It never writes before you say yes. For each agent it prints a unified diff of every file it would change, then asks once. --yes skips the question. --remove takes out only what this command put in.

The hooks go into the hooks table of ~/.claude/settings.json and ~/.codex/hooks.json. Each hook command is the full path of this Python with -m ramabana.peer_hooks, so it runs this ramabana whatever is first on PATH. A hook group is ours when one of its commands has ramabana.peer_hooks or peer-hook in it, so the ramabana peer-hook groups of older setups are replaced or removed too. A second run replaces our groups where they stand and changes nothing when they are equal. Your own hooks and settings stay as they are. If the file is not valid JSON, the command names it and writes nothing for that agent.

merge_hooks does the merge. An empty block removes our groups, and an event with no groups left is dropped:
