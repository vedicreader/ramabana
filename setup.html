setup

The first run: ramabana starts inside its own tmux server, offers to install tmux when it is missing, and ramabana --doctor says what it found.

This module holds what has to happen before a session starts. The terminal session runs best inside tmux, a terminal multiplexer that divides one window into panes. tmux gives Ramabana a split for the now pane, the live view of the turn described in pane, and with its extended keys setting on it delivers shift+enter to the program as a key of its own, which the session uses to queue a message for the next turn. So the first run starts Ramabana inside a tmux server of its own, offers to install tmux when it is missing, and ramabana --doctor reports what it found. The module also decides whether the code index needs rebuilding.

Extras and scripts

Every console script that the package installs starts in this module, so it imports only fastcore and the standard library, and never ramabana.core. That keeps a script quick to start and lets it check for its dependencies before it imports them.

installed(mod) says whether a module would import, without importing it. need(extra) checks the modules an extra provides, as listed in EXTRAS, and returns the install command for the ones missing, or '' when all are there. SCRIPTS names, for each console script other than ramabana, the module whose main it runs and the extra it needs. Looking up one of those names on this module returns that main, or, when its extra is missing, a stand-in that prints the install command and exits with status 2. ramabana.core re-exports installed, need, EXTRAS and SCRIPTS.

The config

Each session gets a tmux server of its own, started as tmux -L ramabana-<id> with the config file <cfg>/tmux.conf. A new server reads the current config and inherits the current environment, so a second session never picks up the first one’s API keys or virtual environment. That server never reads ~/.tmux.conf, and your own tmux setup is left as it was.

Extended keys are a tmux setting that passes key combinations such as shift+enter through to the program in the pane, instead of folding them into plain enter. tmux_conf(version) returns the config for a given tmux version, adding only the lines that version understands: extended-keys arrived in tmux 3.2 and extended-keys-format csi-u in 3.5, and an older tmux prints an error for each line it does not know. tmux_version reads the version from the output of tmux -V. The config claims true colour (RGB) only when $COLORTERM says the terminal draws it. The cell below prints the config for tmux 3.5.

The relaunch

Setup collects everything about the tmux that Ramabana runs in: the config, the relaunch into it, the install offer and --doctor.

Setup.launch runs before an interactive session starts. Outside tmux it replaces the current process with tmux new-session on a new server, running the same command line in the same folder. Quitting Ramabana then ends that tmux session and returns you to your shell. launch does nothing for a one-shot prompt, for --json, when stdin or stdout is not a terminal, and when --tmux off or $RAMABANA_TMUX=off says to stay out of tmux. It also needs tmux 3.0 or later. The relaunched process has $RAMABANA_WRAPPED set, so it never relaunches a second time. Inside tmux, --pane auto then opens the now pane.

The server is set to destroy-unattached, which ends the session when you detach or close the window, so Ramabana never keeps running where nobody can see it. The history is saved, and --resume latest reopens it. The command runs under sh with a short wrapper, HOLD, that waits for enter after a non-zero exit, so an error stays on screen instead of vanishing with the tmux session.

Inside a tmux server of your own, launch turns extended-keys on for that server when it is off. The change lasts until the server exits, and only programs that ask for extended keys receive them.

Every effect on the outside world goes through an argument of Setup: which, system, run, execvpe, ask and isatty, plus environ, argv and cwd. The examples pass fakes for all of them, so they run without tmux and change nothing.

from types import SimpleNamespace
import tempfile

class Box:
    "Programs on PATH, the commands run, the prompts shown and the exec made."
    def __init__(self, have=('tmux',), version='tmux 3.5a', system='Darwin', answer='', ext='on'):
        self.have, self.version, self.system, self.answer, self.ext = set(have), version, system, answer, ext
        self.calls, self.asked, self.execd = [], [], None
    def which(self, name): return f'/bin/{name}' if name in self.have else None
    def run(self, cmd, **kw):
        self.calls.append(list(cmd))
        if 'install' in cmd: self.have.add('tmux')
        return SimpleNamespace(returncode=0, stdout={'-V': self.version, 'show': self.ext}.get(cmd[1], ''))
    def ask(self, q): return self.asked.append(q) or self.answer
    def execvpe(self, *a): self.execd = a

config.toml

~/.config/ramabana/config.toml holds this machine’s settings: one file, edited by hand, that every Ramabana on the machine reads. A session started with another --cfg, and an app that embeds Ramabana with a config folder of its own, read the same file and never write into their own folder for it. $RAMABANA_CONFIG names another file; the tests use it.

A value can come from four places, and the first that has one wins:

Source Example
a command-line flag --model gpt-5.4
an env var $RAMABANA_MODEL, or $LEELA_MODEL inside Leela
config.toml [jobs] turn = "gpt-5.4"
the built-in default claude-opus-5-5

KEYS lists every key: its type, the env var and the flag that beat it, what it sets, and the values it may take. The tables are [jobs], the model each job runs on; [window], the numbers the window guard works with; [compaction]; [runtime], what a model is started with; and [cli], the defaults of the terminal session’s flags that take a value. [jobs] image is the OpenAI-compatible model generate_image draws with. [azure] holds Azure OpenAI’s endpoint, which $AZURE_OPENAI_ENDPOINT beats, read as named with no prefix (Key.plain), and the api_key_env that names the env var holding its key. A key an earlier release read, such as azure.deployments, is reported with what to do instead (RETIRED_KEYS). A [model."NAME"] table corrects the numbers fastllm’s table gives one model: max_input_tokens, max_output_tokens and supports_images. Given model_id, the same table defines a model of that name, with runtime, base_url, api_key_env, api_name, vendor_name and ctx; core registers it.

load_config reads the file again only when it changes. An entry it cannot use takes its default and gives one warning, which Agent.problems and ramabana config show repeat: a key nobody knows, with the nearest one it might mean; a value of the wrong type or outside its choices; a file that is not TOML. Nothing raises.

Installing tmux

When tmux is missing, offer_install asks once whether to run the command that installs it, and shows the command: brew install tmux on macOS, sudo apt-get install -y tmux or sudo dnf install -y tmux on Linux. installer picks the command from what is on PATH. The command runs attached to the terminal, so sudo can ask for a password.

The answer is stored in <cfg>/setup.json. A no is never asked again, and neither is a yes whose install worked. Ctrl+c at the prompt, or an install that failed or was interrupted, stores nothing, so the next run asks again. ramabana --doctor asks even after an earlier no. Without tmux, the session starts in the current terminal and prints one line on how to get the now pane.

The first example says yes on a Mac with Homebrew, and the session relaunches in the tmux it installed. The second says no on Linux, and a second launch does not ask again:

Whether the code index needs to run

The search_code tool searches a code index that kosha builds over the installed packages and the open folders. Rebuilding it, called a sync, takes time, so the session skips it when nothing it reads has changed.

index_gate(cfg, roots) decides this without importing kosha. It takes a fingerprint, index_state, of what a sync would read: the installed distributions that importlib.metadata finds, with their modification times (pkg_state), and for each folder its git HEAD and a digest of git status with the modification times of the paths it names (root_state). Outside git, a folder’s fingerprint is the newest modification time among its entries. It returns the fingerprint and a reason to run kosha, or '' to skip it. The reason is '' when the fingerprint matches the one the last good sync saved in <cfg>/kosha-state.json and each folder’s .kosha/code.db and kosha’s package database, kosha_env_db(), exist. Otherwise index_changes says what changed, such as packages changed: +foo 1.2.

After a good sync the session calls save_index to store the new fingerprint. Either way log_index appends one line to <cfg>/kosha.log, and --doctor shows the last line through last_index. The example walks a fresh folder through a first sync, a missing index, an unchanged state and a new package:
