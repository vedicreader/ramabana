runtime

Run model turns, keep each conversation inside its context window, and capture what native engines print.

Native output

A local engine such as LiteRT is a C++ library loaded into the Python process. It prints its messages straight to file descriptors 1 and 2, the process’s standard output and standard error. These messages never pass through Python’s print or logging. When a turn fails, for example because the prompt was longer than the model’s window, one of those lines is often the only explanation. This section captures the descriptors during a model call and keeps the lines that explain a failure.

interesting picks those lines out of captured text. It drops the engine’s routine startup messages. It keeps lines that mention an error, a failure, an exceeded limit or running out of memory. It returns the last limit of them.

source

interesting

def interesting(
    text, limit:int=4
):

The error lines in captured output, without routine startup messages.

Engines have no log level to filter on. interesting matches words. In this log three lines are startup messages and one line says why the call failed:

log = '''Created TensorFlow Lite XNNPACK delegate for CPU.
Loading model from /models/gemma-e4b
I0000 00:00:1730000000.000000 metal delegate ready
ERROR: input tokens 21014 exceeds max_num_tokens 16384
'''
interesting(log)

Repeated lines collapse into one, and only the most recent limit lines are kept. An engine that fails on every step of a tool loop prints the same error many times, and the user needs to see it once.

test_eq(interesting('ERROR: oom\nERROR: oom\nERROR: oom'), ['ERROR: oom'])
interesting('\n'.join(f'error {i}' for i in range(10)), limit=2)

captured is a context manager that records what is written to descriptors 1 and 2 inside its with block. It copies the output and does not hide it. The bytes still reach the terminal. The last 8,000 bytes of each descriptor (MAX_KEEP) are kept in cap.text. cap.problems runs interesting over that text.

Only one captured block is active at a time across all threads. Two threads that redirect the same descriptor would restore each other’s copies and leave the real descriptor detached. A thread that cannot take the lock within half a second runs its block without capture. Setting RAMABANA_NO_NATIVE_CAPTURE to 1, true or yes turns capture off.

capture(fn, *args) wraps a single call. It calls fn inside captured and returns a pair of the result and the problem lines the engine printed. A call can succeed and still print a warning worth showing. Here the engine truncated its input:

def _engine_call():
    os.write(2, b'Created TensorFlow Lite XNNPACK delegate for CPU.\n')
    os.write(2, b'WARNING: input exceeds max_num_tokens 16384, truncating\n')

capture(_engine_call)

When fn raises, capture attaches the problem lines to the exception as native_output and raises it again. Native failures often arrive as an exception with an empty message. The attribute keeps the real explanation with the exception:

def _engine_dies():
    os.write(2, b'ERROR: failed to allocate 4.00 GiB for KV cache\n')
    raise RuntimeError('')
try: capture(_engine_dies)
except RuntimeError as e: err = e
err.native_output

Sizing a conversation

These functions decide when a conversation has grown too big for its model. Each limit is a fraction of the context window and not a fixed number of tokens. The same code then works for a 4k-token local model and a 200k-token hosted one. A fixed reserve fails on the small window. With 16k tokens held back from a 4k window, every turn is due for compaction, and the agent compacts a two-message conversation forever.

estimate_tokens counts the tokens in a text. threshold gives the token count at which compaction becomes due, and should_compact compares a count with it. halvings returns the original budget followed by successively halved budgets. Use it to retry a request whose size was only estimated. No value is larger than the original budget. halvings(0) returns [0].

Parameter Default Meaning
tries 3 Number of values returned
floor 256 Minimum for each value after the first, unless the original budget is smaller

estimate_tokens

def estimate_tokens(
    text, count:NoneType=None
):

Tokens in text: exact via count when a tokenizer is at hand, CHARS_PER_TOKEN otherwise.

estimate_tokens uses the model’s own tokenizer when you pass one as count, and otherwise divides the length of the text by CHARS_PER_TOKEN (3.25). The estimate is rough, and close enough for budgeting.

estimate_tokens('the exporter writes one module per notebook'), estimate_tokens('', ), estimate_tokens('x' * 400)

threshold(ctx) holds back a reserve below the window. The reserve is the full RESERVE of 16,384 tokens for a large window and at most a quarter of the window for a smaller one. Without the quarter-window cap, a 4k model is due for compaction before its first turn. The reserve argument overrides the default, which is config.toml’s window.reserve when set. threshold returns None when the window size is 0 or unknown.

A large window is rarely the limit. A model works best well below its window, and every call re-reads what the conversation holds. Compactor therefore adds two absolute lines in tokens:

line default config key what happens past it
soft SOFT_LINE, 150,000 compaction.soft the next turn that starts at a clean boundary hands off to a fresh context
hard HARD_LINE, 250,000 compaction.hard the conversation is compacted, or at the window’s threshold when that is lower

done_items reads the Done list out of a summary, which a handoff keeps as a memory note.

threshold(200_000), threshold(32_768), threshold(4096)
test_eq(threshold(4096), 3072)
test_eq((halvings(4000), halvings(128), halvings(0)), ([4000, 2000, 1000], [128, 128, 128], [0]))   # no retry is larger than the first budget
test_eq(threshold(0), None)
should_compact(3000, 4096), should_compact(3072, 4096)

Reading a conversation

A backend stores its conversation as a list of message dictionaries in urai’s format, which is the same for every model. Each message has a role (user, assistant or tool) and content. An assistant message that calls tools also carries tool_calls, and the result of each call comes back as a tool message. Compaction reads this list directly, using urai’s resp_text for a message’s text and tool_rows for its tool calls.

The examples below use this four-message conversation: a request, a tool call, the tool’s result, and the reply.

hist = [
    {'role': 'user', 'content': 'the exporter duplicates cells, please fix it'},
    {'role': 'assistant', 'content': 'Reading the exporter.',
     'tool_calls': [{'function': {'name': 'view_file', 'arguments': {'path': 'nbdev/maker.py'}}}]},
    {'role': 'tool', 'content': 'def _make_exists(self, cells):\n    with self.fname.open("a") as f: ...'},
    {'role': 'assistant', 'content': 'It appends, so a second export duplicates every named cell.'},
]
[(m.get('role', '?'), resp_text(m)[:40], [name for name, _ in tool_rows(m)]) for m in hist]

serialise writes a list of messages as the text a summarizing model reads. Each message goes in a <message> tag, with its tool calls named in a <tool-calls> tag. Each text is clipped to mx characters (2,000 by default), and a clipped text ends with an ellipsis. An empty list gives (no new messages).

summarise_prompt builds the request sent to the summarizing model. With no earlier summary it asks for a new one in a fixed format: goal, constraints, progress, key decisions, next steps and critical context. When split_previous finds an earlier summary, it asks for that summary to be updated with the new messages instead. extra adds a line saying what the summary should focus on.

The summary is usually written by a cheaper model with a smaller window, so max_tokens caps the size of the request. When the whole request does not fit, the earlier summary is cut to a quarter of the budget, and the messages after it fill what is left, cut from the end. The instructions come last and are kept whole while the budget can hold them.

SURGICAL_POLICY sets the budgets: 2,000 tokens for a user message, 150 for the assistant’s text, 60 for a tool call and 35 for a result. The user’s own words are kept nearly whole, and tool results are cut hardest. policy overrides any of them:

print(surgical_history(hist, policy={'result': 8, 'assistant': 20}))

The narrative digest

A summary made by a model loses detail, and the surgical form cuts the assistant’s own words to 150 tokens. A long agent turn is mostly tool output, so a summary of its transcript is mostly a summary of tool output. The digest keeps what the people in the conversation said, and makes the tool work small:

  • the user’s messages, nearly word for word (§), without the harness’s notices;
  • the assistant’s prose, nearly word for word (»);
  • one line for each tool call (▶): its name, its main target, and ok, error: with a short error text, or no result.

call_target finds the main target: the first of TARGET_KEYS that the call has, else its first text argument. call_failed says whether a result reports a failure: an ERROR: text from a tool, or a command that exited with a code that is not zero.

Reorienting the model

After compaction the model sees a summary where its conversation used to be. reorient writes the reminder placed after the summary. The reminder says whether the Python kernel survived. The model then knows whether its variables still exist. The reminder tells the model that skill text it read earlier is no longer in context and has to be read again with read_skill. It names the skills when skills is given. The reminder also tells the model not to answer a finished request a second time. If the latest request is complete, the model replies in one line and waits. REORIENT is the reminder with the default arguments.

source

    kernel_alive:bool=True, skills:tuple=()

The system reminder placed after a compacted or otherwise rewritten conversation.

When the kernel restarted, the reminder says the namespace is empty and tells the model to rebuild its variables. When the kernel survived, the reminder tells the model to inspect its variables with inspect_python() and not to rebuild them.

assert reorient(kernel_alive=False) != reorient()

Notices on the way in

Before a prompt reaches the model, prompt_notices checks it with a few string tests and returns notices: short instructions that tell the model how to treat the prompt. They follow the UserPromptSubmit hook in Answer.AI’s aai-coding prompts, and each one prevents a mistake models often make.

  • A prompt ending in ? is a question. The model answers it and stops, without starting the work it implies (Q_NOTICE).
  • A prompt containing “please read”, “read the” or “have a look at” asks the model to read the target in full before answering (READ_NOTICE).
  • A bare approval such as “go”, “ok” or “do it” approves only what the user explicitly agreed to, not everything the model proposed earlier (APPROVAL_NOTICE).
  • A prompt starting with “BTW” is a side request. The model answers it and then goes back to the task it was on (BTW_NOTICE).
  • A prompt starting with a verb such as fix, add, run or rename, or ending in as NAME, asks for action. The model does the work and checks it before replying (ACTION_NOTICE).

Three one-character prompts are shortcuts and get only their own notice: . continues the agreed task, ; asks for the last answer in simpler words, and , asks what the user needs to answer next.

Fitting a notebook into the prompt

A prompt can carry the user’s open notebook inside a <notebook> tag, one <cell> per cell. Each cell has a compact attribute that the user sets: keep, auto or discard. compact_notebook_context leaves the prompt alone when it fits. When it does not, it removes discard cells, then auto cells, each in notebook order, until the prompt fits. It never removes a keep cell. A <context-compacted> tag records how many cells were left out.

fits is a function that says whether a prompt fits. The agent passes the backend’s fits, so the decision is made against the real window of the model in use.

source

compact_notebook_context

def compact_notebook_context(
    prompt, fits

Reduce a tagged notebook only when prompt does not fit. A keep cell is never removed.

The notebook below has three cells, one with each setting, and a question about it. When everything fits, the prompt comes back unchanged:

nb = '''<notebook path=analysis.ipynb>
<cell id=1 compact="discard">print(load_everything())  # 900 lines of output</cell>
<cell id=2 compact="auto">df = read_csv('sales.csv')</cell>
<cell id=3 compact="keep">model.fit(df)  # the cell the question is about</cell>
</notebook>

why did the fit fail?'''
print(compact_notebook_context(nb, fits=lambda s: True))

With a lower limit the discard cell goes first, and <context-compacted> records it:

The compactor

Compactor decides when a backend’s conversation is due for compaction, and carries it out. It keeps the most recent messages as they are. It replaces everything older with one message: the session ledger, then a digest of the older messages, then the reorient reminder. The ledger comes from the ledger function, when given, and goes first. The digest strategy, the default, calls no model. With overflow='summary', a digest that is still over digest_budget has its oldest lines summarised by the summariser(prompt, sp) function you pass to compact. The digest’s newest lines and the ledger are never summarised. With strategy='surgical' it uses surgical_history. With strategy='summary' it asks the summarizer for a summary of all the older messages, as below.

due(backend) says whether the backend has crossed its threshold. compact returns the summary, or '' when it did nothing, and note says what happened either way. on_compact, when given, is called with each new summary. If the summarizer fails or returns nothing, the conversation is left alone. When you give the summarizer’s window as summary_ctx, no request is larger than it. fold_summary splits a history that is too large for one request into runs that each fit (transcript_runs). It summarises the first run and updates that summary with each run after it. A history of any length can compact this way. A failed or empty call is retried at half and then a quarter of the request size.

Compaction has its own class and is not a rishi callback. It needs a second model call and then replaces the first model’s history. A callback does not do both.

source

Compactor

def Compactor(
    reserve:NoneType=None, # None reads config.toml's `window.reserve`, else `RESERVE`, each time
    keep_recent:NoneType=None, # None reads `window.keep_recent`, else `KEEP_RECENT`
    auto:bool=True, # the agent compacts on crossing the threshold only when true; `Compactor` itself ignores it
    kernel_alive:bool=True, # whether the kernel survived; passed to `reorient`
    on_compact:NoneType=None, # called with each new summary
    strategy:str='digest', # 'digest', 'surgical' or 'summary'; only 'summary' always calls a model
    soft:NoneType=None, # None reads `compaction.soft`, else `SOFT_LINE`
    hard:NoneType=None, # None reads `compaction.hard`, else `HARD_LINE`
    ledger:NoneType=None, # a function that returns the session ledger, put before the digest
    overflow:NoneType=None, # 'cut' or 'summary': what a digest past its budget does with its oldest lines; None reads `compaction.overflow`, else 'cut'
):

Decide when to compact, and do it.

budget(ctx) is how many tokens of recent conversation survive compaction: KEEP_RECENT (20,000), capped at half of what the window holds besides the system prompt and tools (overhead). Without the cap, a 4k model would count its whole conversation as recent, find nothing older to summarise, and report everything is recent; nothing to compact until the engine refused the turn. compact also keeps at most about half of the conversation.

The kept part can start at a user message or at an assistant message. It never starts at a tool result without the call that asked for it. An agent turn often has one user message and then hundreds of tool calls. If the kept part had to start at a user message, such a turn would keep nothing, and the model would lose its last steps. When the kept part has no user message, the summary message also holds the user’s last request word for word, up to PIN_CHARS characters. The ledger also holds every request, so a request is not lost when it is older than the pinned one. When the ledger holds the last request word for word, the pin is left out, and the request is not repeated.

c = Compactor()
c.budget(200_000), c.budget(32_768), c.budget(4096)
test_eq(c.budget(4096), 2048)
test_eq(c.note, 'not compacted')

    def __init__(self, used, ctx): self.used_tokens, self.spec = used, type('Spec', (), {'ctx': ctx})()

Answers, without the thinking

Reasoning models think before they answer. Some runtimes return the thinking in a separate channel. Others leave it in the reply, wrapped in <think>...</think>. The agent’s one-shot jobs read the reply as data, such as a label, a summary or a completion to insert. The thinking has to come off first. A classifier that returned the model’s reasoning would return no label.

answer_only removes the thinking from a finished reply, using urai’s split_think.

source

A one-shot reply with the model’s thinking removed, however the runtime left it.

In the simple case the thinking is wrapped in a pair of tags:

Some chat templates open the <think> block in the prompt itself, so the reply starts inside the thinking and only the closing tag appears. answer_only handles that too. A reply that opens a block and never closes it, because it hit the output cap, has no answer and gives ''. A reply with no tags comes back as it is.

answer_only('<think>a</think>yes')

A model whose template opens the thinking block does so at every step of a turn. After each tool call, the next reply begins inside a new thought. prefills_think tells whether a model’s template does this. It renders a one-message prompt and looks for an unclosed <think>. For such a model RishiBackend passes the stream through a ThinkFilter. The filter drops text until it sees </think>, lets the rest through, and starts dropping again after each tool call. Use answer_only on a finished reply and ThinkFilter on a stream. The filter also counts the characters of thinking (thought) and of answer (answer). The backend uses the counts to report a turn that spent all its output thinking. One-shot jobs avoid the problem by asking the model not to think.

Backend

Backend is the contract the agent uses to talk to a model. One backend holds one conversation. It starts the model on first use, sends a message with send or streams the reply with stream, asks one-shot questions with oneshot, counts tokens, and replaces or restores the conversation’s history. Subclasses supply the engine-specific methods whose names start with an underscore. RishiBackend, further down, is the one the agent uses.

send, stream and oneshot do not raise when the model fails. A model that cannot start, a stream that breaks and an empty reply all become text: note holds the latest status, problems keeps the last 20 problem lines, and turn_error says why the last turn failed. A caller can always show the user what the backend returned.

The examples below run the base class itself, which has no engine, to show these rules.

RishiBackend

RishiBackend is the only implementation of Backend, because rishi runs every model, local or hosted. It turns a ModelSpec (a model’s name, runtime, id and window, from core) into a rishi Chat, converts rishi’s usage into Usage, and handles what differs between runtimes:

  • The window goes to LiteRT as the engine’s token ceiling, max_num_tokens, and to llama.cpp and ollama as n_ctx.
  • A Claude model is asked for high reasoning effort (CLAUDE_EFFORT) unless a higher-precedence source names another level. In order of precedence these are an effort argument to the backend, RAMABANA_EFFORT, the model’s effort setting and runtime.effort.
  • On MLX, one-shot questions run in a separate conversation on the same engine, so a completion never sees earlier completions.
  • A local model’s window is set from the window it was trained for, capped by Ramabana’s limit for that model, and narrowed again if the engine reports a smaller one.
  • When a hosted service refuses the tool schemas, the backend moves that model to the tags channel and retries once. On that channel the schemas travel in the system prompt and calls come back as <tool_call> blocks in the text.
  • When a reply on the tags channel describes a tool call instead of making one, the backend sends one reminder (TAG_REMINDER) asking the model to make the call.

rishi adds two callbacks to a chat by default: a reminder on every message, and a sliding window that forgets old messages without summarising them. RishiBackend removes both (ROUTINE_CBS). Compactor does that job. LiteRT runs the tool loop inside the engine. The text a model writes before a tool call never reaches Ramabana. QUIET_RUNTIMES lists such runtimes, and narrates is False for them.

LiteRT models run on the GPU by default. rishi asks for the GPU, and falls back to the CPU with a warning when the build has no GPU support. RAMABANA_LITERT_BACKEND=cpu pins a model to the CPU, and gpu asks for the GPU explicitly. The runtime.litert_backend setting does the same. A backend= argument, or eng_kw={'backend': ...}, takes precedence over the variable. RISHI_LITERT_GPU=0 stops rishi asking for the GPU at all.

Runs

A run is one piece of model work that can be cancelled: the turn the user started (kind='root'), or a sub-agent that the turn delegated to (kind='child', made with child). Runs form a tree. Cancelling a run cancels everything under it, and the tool calls of the whole tree count against one budget, through draw.

A run starts pending, becomes running with start, and ends completed, refused (a mod turned the turn down before any model call), failed, cancelled, detached or terminated. cancel asks the backend to stop and waits up to grace seconds. A run whose backend does not stop in time is detached: the caller treats it as over and ignores anything the model sends later. terminate closes the backend outright.

A run also keeps what the user should see while it works. status is the last line the model wrote before its latest tool call. notes keeps up to 100 such messages for the now pane, the live view beside the terminal (pane), and write appends a line to the run’s transcript file when it has one. tell queues a message from the user for a running sub-agent, and drain_inbox hands the queued messages over. give_back returns messages that were handed over and never read to the front of the inbox, so a turn a mod refused leaves them for the next one. air returns a reminder to tell the user where the work stands once 8 tool calls in a row have gone by with less than 100 characters said before them. repeated counts identical calls with identical results in a row, so the agent can tell a model that it is looping.

Once its run is cancelled, a backend’s stream stops yielding, drops what the model sends later, and does not retry:

class _CancelStream(Backend):
    def __init__(self):
        from ramabana.core import ModelSpec
        super().__init__(ModelSpec('cancel-test', 'fake', 'fake/cancel', ctx=1000))
        self.first, self.release, self.calls, self.recoveries = threading.Event(), threading.Event(), 0, 0
    def _start(self): return self
    def _stream(self, msg, **kw):
        self.calls += 1
        yield 'first'
        self.first.set(); self.release.wait()
        yield 'late'
    def cancel(self): self.release.set(); return True
    def _usage(self): return Usage()
    def _recover(self, e): self.recoveries += 1; return True

A tool whose schema cannot be built must not look like a model that cannot run. Such a tool can be a plug-in whose file was deleted after it loaded, or a tool with no type for a parameter. When the chat fails to start, start builds each tool’s schema. It leaves out each tool that fails, says so in a notice, and starts again. Only a second failure marks the model unavailable.

from urai.msgs import mk_toolspec
class _Specs(Backend):
    def _start(self): return [mk_toolspec(t)['function']['name'] for t in self.tools]
    def _refresh(self): self.chat = self._start()
def echo(x:str):
    "Echo `x`."
    return x
def untyped(x):
    "A parameter with no type, so no schema."
    return x
b = _Specs(ModelSpec('specs', 'fake', 'fake/specs', ctx=1000), tools=[echo, untyped])
test_eq(b.start(), ['echo'])
assert 'tool untyped is left out' in b.problems[0] and 'unavailable' not in b.problems[0]
b.refresh('', [echo, untyped])
test_eq((b.chat, b.note), (['echo'], '1 tools'))
