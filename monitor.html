monitor

Folder watches checked between turns, with a standing review that runs when files change.

This module runs two kinds of work outside the turn you are typing in. A folder review reads changes that someone else made to a watched folder and reports on them at the start of your next turn. The beat runs scheduled work on a timer, with or without an open session. The beat section is at the end of the page.

Folder reviews

A folder watch is a standing request to review changes under a folder. You ask the agent to watch a folder and give it instructions such as “check each change for correctness”. Whenever files under that folder change, a reviewer reads the diff and follows the instructions. The report appears in your next turn.

The model opens a watch with the shalya watch tool: watch(target, kind='folder', instructions=..., pattern=...). pattern is one string of globs separated by commas or spaces, such as *.py,*.md. A glob matches a file name or a whole posix path. An empty pattern matches every file. The tool stores the watch as a row in the vault, beside the scheduled page, search and reminder watches. list_watches and cancel_watch also see the row.

Monitors does the reviewing. Monitors.sync copies the vault’s folder rows into the session. Monitors.check calls sync first and picks up any folder watch the model opened since the last check. A host without a vault gives the model no tool to open a folder watch. Code can open one with Monitors.add.

A new folder watch takes a baseline: a snapshot of the folder at that moment. Only later changes are reviewed. The reviewer receives the watch’s instructions and the changes. It receives nothing from the conversation that created the watch. The instructions must say everything the reviewer needs. add refuses a watch with empty instructions.

Each completed review goes into a queue. Monitors.drain empties the queue, and the agent adds the drained reviews to its next prompt with review_notice. The queue holds PENDING_MAX reviews and drops the oldest. Each review is also noted to the user. A review that has text is filed in memory under the key folder-review: plus the watch id. A newer review of the same folder replaces the older one. The agent runs Monitors.check in a daemon thread between turns.

Change detection

snapshot records the text of every readable file under the watched folder that matches the pattern. changed compares two snapshots and returns the files added, edited or removed. report lists the changed files with their added and removed line counts, then appends the unified diffs. summarise returns a one-line count such as 1 added, 1 edited. A file larger than SNAP_MAX_BYTES is recorded as its size alone. A change to it shows as a changed size with no diff.

Constant Value Limit
SNAP_MAX_FILES 2000 Files in one snapshot. Later files in sorted order are ignored.
SNAP_MAX_BYTES 400,000 Characters of one file.
REVIEW_MAX_CHARS 24,000 Characters of change report in one review prompt. Also the clip for review_notice and beat_notice.
PENDING_MAX 20 Queued reviews.
DFLT_SETTLE '20s' Settle window of a new folder watch.

A folder watch’s settle window is the least time between two reviews of one folder. Changes that arrive inside the window wait and go into the next review together. A burst of saves produces one review. check(force=True) ignores the window.

Reviewer

The reviewer is a read-only sub-agent. It has the session’s read tools and no write tools. REVIEW_SP is its system prompt. Reviews use the session’s sub-agent step setting. Under auto, each review gets SUB_MAX_STEPS (80). A numeric setting gives each review that many steps, up to SUB_STEP_CEILING (400). Monitors reads get_steps before each review. Without that callback, it uses auto. The budget is passed to the backend as max_steps. Urai counts each approved tool call as one step, including calls in a batch. A quiet backend gets twice that budget to allow for status calls. A separate read-tool allowance permits four calls per requested step. The reviewer cannot edit the watched folder. It describes any fix instead of making it. Without a backend to run it on, the change is recorded with status unreviewed. A review that raises an error is recorded with status error. The baseline moves forward on every review attempt, including a failed one. A change is never reviewed twice.

The same flow runs through the model’s tools. VaultLike stands in for a vault host. It stores watches as rows and keeps filed notes in a list. The watch tool opens a folder watch. The next check picks it up through sync and takes its baseline. An edit then produces a review filed under the key folder-review:w1. After cancel_watch, the next check removes the watch from Monitors.

from ramabana.tools import MemoryHost, WatchHost, watch_tools

class VaultLike(MemHost, MemoryHost, WatchHost):
    "A host whose watches table is a list and whose memory is the notes it was handed."
    def __init__(self, files): super().__init__(files); self.rows, self.notes = [], []
    def watch(self, target, action='remind', every='1d', note=None, **params):
        w = dict(id=f'w{len(self.rows)+1}', kind=action, target=target, every=86400, note=note, runs=0, last_status='', **params)
        self.rows.append(w); return w
    def watches(self, due_only=False): return list(self.rows)
    def unwatch(self, wid): self.rows = [r for r in self.rows if r['id'] != wid]; return True
    def poll(self): return {'checked': 0, 'ran': 0, 'results': []}
    def remember(self, text, title=None, tags=(), key=''): self.notes.append((title, key, text)); return dict(doc_id='d1', title=title)
    def memory_search(self, query, limit=8): return []
    def memory_tree(self, document=''): return []
    def memory_read(self, node_id): return {}
    def memory_forget(self, doc_id): return False
    watch_actions = ('url', 'remind', 'web', 'folder')

vh = VaultLike({'/proj/a.py': 'one\n'})
vm = Monitors(vh, get_backend=lambda: FakeBackend(SPEC))
wt = {t.__name__: t for t in watch_tools(vh)}
print(wt['watch']('/proj', kind='folder', instructions='Review each change.'))
test_eq(vm.check(force=True), [])
test_eq([w.id for w in vm.all()], ['w1'])
vh.write('/proj/a.py', 'two\n')
rec, = vm.check(force=True)
test_eq((rec['watch_id'], rec['review'].split('\nstate:')[0]), ('w1', 'sub answer'))
test_eq(vh.notes[-1][:2], ('folder review: proj: 1 edited', 'folder-review:w1'))
wt['cancel_watch']('w1')
test_eq(vm.check(), [])
test_eq(vm.all(), [])

The beat

Some work must run on a timer with or without an open session, such as a nightly job that learns from the day’s sessions. pobblebonk does the timing. It is a small scheduler that installs one job with the operating system’s scheduler (cron, launchd or Windows Task Scheduler). It keeps its schedules, the work they fired and the notes that work left in a SQLite database.

A schedule is a name, an interval and a callback. The callback runs when the schedule fires. A beat is one pass over the schedules. It runs every schedule that has come due. A note is a short title and body that a callback leaves for the next reader. Several readers can share one database. Each reader sees each note once.

This module holds the Ramabana side of that arrangement. on_tick(name) registers the callback for a schedule from Python. pob opens the shared database, or returns None when pobblebonk is not installed. beat_notes returns the notes that a reader has not seen yet. beat_notice wraps them in a <beat> block, which the agent adds to its next prompt. beat_notes reads under the reader name POB_READER by default. A session reads under POB_READER plus a colon and its session id. beat_join starts the session’s reader at the newest note. Every open session therefore sees every note made after it began. Packages that define recurring work own their schedules. Ramabana runs them.

on_tick

def on_tick(
    name
):

Register the callback a fire of schedule name runs.

tick is the ramabana-tick command. Run without options, it registers the callbacks, runs one beat, prints how many schedules ran of those that fired (N ran of M fired, unless --quiet) and exits. With no schedules registered it does nothing and exits with status 0. --install schedules ramabana-tick --quiet in pobblebonk to run every --every seconds. --uninstall removes it. beat_command builds that command line and quotes the path for the platform’s shell. heartbeat returns the pobblebonk scheduler module, or None.

launchd and cron start a job on /usr/bin:/bin. That PATH holds neither claude in ~/.local/bin nor Homebrew’s git-lfs. Off Windows, beat_command runs the beat through /usr/bin/env with the PATH of the shell that installed it. --install prints that PATH. The beat carries only PATH. A key exported in a shell profile does not reach the beat. After you install a tool in a new folder, run ramabana-tick --install again to make the beat find it.

--install warns on stderr when its PATH is the launchd default, or when it cannot find one of BEAT_TOOLS (claude, git, git-lfs) or the ramabana-tick it schedules. The warning names what is missing (beat_missing). A claude that starts with #!/usr/bin/env node also needs node on that PATH. --install still installs. The warning tells you to run it again from a terminal whose shell finds the missing items.

beat_problems reads the launcher that the scheduler runs. It reports four problems, each with the command that fixes it. The problems are a launcher written before the PATH was carried, a tool that this shell finds and the launcher’s PATH does not, a ramabana-tick that is gone, and a beat.env that other users can read. A session adds these lines to its first beat note. ramabana-tick --check prints them and exits with status 1 when there are any.

Never put keys in the launcher. Any user can read it. Put keys in beat.env beside config.toml (~/.config/ramabana/beat.env), one NAME=value per line, and run chmod 600 on it. Each beat loads beat.env with python-dotenv before any schedule runs. It sets only the names that its environment lacks. It refuses a file that other users can read. The api_key_env setting in config.toml names a variable, and beat.env supplies its value. An ANTHROPIC_API_KEY in beat.env makes Claude Code bill the API instead of the subscription.

launchd starts no second beat while one runs. A hung fire stops every schedule. A beat stops itself after --limit seconds. When --limit is 0, BEAT_LIMIT applies (six hours). Every schedule in that beat shares the limit. Off Windows, a SIGALRM raises BeatTimeout in the running fire. The SIGTERM that launchd sends when it replaces the job does the same. pobblebonk records the exception as that fire’s failure, and the beat claims no further fire. A watchdog thread ends the process a minute later if the fire is stuck where no signal reaches. On Windows the watchdog is the only bound. --install --limit N writes the limit into the launcher. Task Scheduler on Windows gives a job the user’s environment. The Windows command therefore does not carry PATH.

An installed package registers a callback through a ramabana.ticks entry point (TICK_GROUP). The entry point’s name is the schedule’s name and its value is the callback. The beat imports the package only when that schedule fires. A slow or broken package costs nothing until then. A package that fails to import fails that one fire. pobblebonk retries the fire or leaves a note. An on_tick callback with the same name replaces the entry point’s callback. A schedule named in LEARNING_TICKS (dhrona) does nothing while learning is off and leaves the note learning is off. Dhrona registers its nightly job this way:

[project.entry-points."ramabana.ticks"]
dhrona = "dhrona.improve:nightly"

Notes can also be written straight to the database with note(title, body). A note with an empty body reads as its title alone:

import tempfile
beat = pob(Path(tempfile.mkdtemp())/'pob.db')
beat.note('watches', '2 of 5 fired')
beat.note('nightly', '')
beat_notes(beat)
['watches: 2 of 5 fired', 'nightly']

After a reader drains the notes, it gets nothing more. Another reader still sees all of them. beat_notes returns an empty list when there is no database or when reading it fails. A locked database never stops a turn.

test_eq(beat_notes(beat), [])
test_eq(beat_notes(beat, reader='another'), ['watches: 2 of 5 fired', 'nightly'])
test_eq(beat_notes(None), [])

class _Broken:
    def drain(self, reader, limit=20): raise RuntimeError('the database is locked')
test_eq(beat_notes(_Broken()), [])

A new reader starts at the first note. A session must not, or it shows the notes of jobs that ended days ago. beat_join starts a reader that has never read at the newest note, so it sees only the notes made after it joined. A reader that has read keeps its place.

beat.note('dhrona', 'ran')
beat_join(beat, 'late'); beat_join(beat, 'another')
test_eq(beat_notes(beat, reader='late'), [])
test_eq(beat_notes(beat, reader='another'), ['dhrona: ran'])
beat.note('abhyasa', 'indexed')
