Outputs

A kernel reports what a cell produced as a stream of messages: text printed to stdout, a result value, a rich display, an error. A notebook stores the same things as a list of dicts in nbformat, the notebook file format. ExecOutcome holds the result of one request in that shape: whether it succeeded, its outputs, its execution count and its error, if any. The terminal, the session log that log_cell writes, and the tests all read the same list.

output_text flattens such a list to plain text, which is what tests, logs and a plain terminal need. The cell below shows each kind of output.

The kernel

Kernel starts and drives a private ipykernel, the standard Python kernel for Jupyter. start launches it in cwd, waits until it is ready, and runs a bootstrap cell that starts Dhrishti inside it. Dhrishti serves the kernel’s namespace from a background thread. The bootstrap prints the server’s port behind a marker, and start reads the marker to set base, the server’s address. The session is registered under the name <project>-pyrepl-<pid>, so another terminal can find it.

execute runs one cell and returns an ExecOutcome. It passes each output to on_output as it arrives, so the terminal can show it at once. complete asks the kernel for tab completions at a cursor position, interrupt stops the running cell, and shutdown stops the kernel, forcing it when it does not stop within timeout. A Kernel that is not running answers execute with an error and complete with no matches, as the second cell shows.

The host

The agent needs a host whose Python tools reach this kernel. Its file, search and web tools stay the ordinary ones. Dhrishti is the piece that changes: it sends the agent’s run_python, inspect_python and variable listing over HTTP to the agent half of the Dhrishti API. Every call it makes goes to /agent/api/..., which needs no token, and none of these paths reads the owner token that opens /api/exec, /api/set and /api/promote. So no tool call can change the owner’s namespace. The only code here that reads the owner token is promote, which runs when the person types /promote.

log_cell keeps the whole session in one notebook, the session log that Dhrishti keeps. The person’s cells go in as code cells with their real outputs, and each agent turn goes in as markdown cells for the prompt and the answer, in the order they happened.

The agent half of a Dhrishti session, in the shape of a kernel a LocalHost can hold.

Dhrishti is everything a LocalHost needs from a kernel: the calls run, inspect, list_vars, log_cell and describe, and the two facts scopes and kind. run always uses the overlay, whatever scope the model asks for, and inspect accepts only the isolated and overlay scopes. Completion, with the namespace described

Tab completion at the Python prompt draws on two sources. The kernel supplies the candidates. Its completer is IPython’s, with jedi behind it, so it knows imports, attribute chains, dictionary keys and file paths. Dhrishti has no completion endpoint, and its view of the namespace covers only top-level names, so it would complete worse.

Dhrishti supplies the descriptions instead. annotate adds the type and shape Dhrishti reports to each candidate that names a live variable, so the menu shows df -> DataFrame [1200×8] rather than df. Reading descriptions needs no token, so they come from the agent half of the API. They are optional: if the lookup is slow or fails, the menu shows the bare names, never an empty list.

Attaching to a session someone else owns

Sometimes the kernel already exists. Leela, for example, runs a Python session with its own Dhrishti server, and you want a Ramabana agent beside it rather than a second kernel. ramabana --attach NAME starts no kernel. It finds the running server and points the agent’s host at it. The other program keeps the person’s prompt, so in this case there is no Python mode, and Ramabana is only the agent.

find_session(attach) turns a name into the server’s address. A URL passes straight through. Otherwise it reads Dhrishti’s registry of live sessions and tries, in order, an exact session name, a name of the form <attach>-pyrepl-<pid>, and the name of the folder the session runs in. When two sessions match it raises with both rather than pick one, and when none matches it names the sessions that are running. sessions() lists the live sessions, which is what /kernels and ramabana --kernels print.

find_session only reads the registry and never calls Dhrishti’s serve_in_kernel again. Called on a session that is already serving, serve_in_kernel returns the right port but also repoints that session’s logs and resets its agent mode, so a readonly session would come back restricted.

Promotion is not available here. The agent’s work shows in the shared session notebook and over the API that the owning program already watches, and the person promotes from that program, which holds the token.

Colour

hl colours a line of Python for the terminal with rich’s syntax highlighter, which uses pygments. Both are already installed for the transcript. It returns a rich Text whose .plain is exactly the source, or uncoloured Text when pygments cannot read it. Colour changes only what is drawn. log_cell, the session notebook and /copy keep the plain source, because text with colour codes in it cannot be pasted back as code.

Typing more than one line

Ui submits a line when you press enter. That suits a sentence and fails for a block of code, because for i in range(3): is not a program yet. code_state(src) uses the standard library’s codeop.compile_command to say whether the text is complete, incomplete, or invalid, meaning it can never compile. On enter, an incomplete buffer gets a new line under a continuation prompt, a complete one runs, and an invalid one is reported at the prompt without a trip to the kernel. An empty line submits what is pending, as at every Python prompt, and pasted text that compiles runs as one cell.

The first cell below lists the cases. The ones after it type a loop line by line, enter a broken line, and paste two statements.

/promote

Values the agent makes live in its overlay. /promote NAME moves one into the owner’s namespace, where it becomes an ordinary variable at your prompt. Promotion is the owner’s act: it is a slash command the person types and never a tool, so the model can ask for it in words but cannot do it. promote(base, name) reads the session’s owner token and calls Dhrishti’s /api/promote. It works only on a kernel this session started. An attached session’s token belongs to the program that started it, and the terminal says so. The test checks that the command runs off the event loop’s thread and that /promote alone prints its usage.

The agent at the Python prompt

--agent-proxy, or /agent_proxy inside a session, makes the session’s agent reachable from Python as ramabana_agent, so code at the prompt can read the agent’s token use or attach a chat callback. ramabana_agents holds every agent bound in that namespace, by label.

AgentBridge runs in the Ramabana process. It serves one HTTP path, /agent, on the loopback address, and answers only requests that carry its random token. It offers a fixed set of operations. usage, turn_usage and chat_usage return token counts and cost for the session, the last turn and the turn’s chat. callbacks lists the chat callbacks that are known and attached, and attach_callback(name) attaches one, on the session’s own thread through dispatch. Anything else is refused. agent_proxy_code writes the source of a small AgentProxy class that calls the bridge, and inject_agent_proxy runs that source in the agent’s overlay with run_python. The terminal also runs it in the kernel itself, so the person’s code sees the proxy too.
