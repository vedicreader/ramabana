core

Shared errors, environment settings, and the rules that decide which model runs each job.

Errors and environment

Ramabana reports a failure in one of two ways. AgentError is a refusal: something the harness will not do, with a message the user can act on, such as a write outside the open folders or a model whose key is missing. It is shalya’s HostError under another name, so a refusal from a tool and a refusal from the agent are caught the same way. Any other exception is a bug, and is left to look like one.

BranchChanged is the refusal raised when a git branch moved while a person was deciding whether to approve a write to it. Nothing was written.

del os.environ['RAMABANA_MODEL'], os.environ['LEELA_MODEL']
env('MODEL', 'gemma-e4b')
'gemma-e4b'

The model tables

MODELS is the table of short model names you can type, such as sonnet or gemma-e4b. Each name maps to a pair: the runtime that serves it, and the id that runtime knows the model by. It is built from smaller tables. LOCAL holds the LiteRT models, MLX the models for Apple silicon, LLAMA the llama.cpp models, CLOUD the OpenAI and Codex models, and the Claude tables come from the catalog in models.

JOBS lists every job the policy can route on its own: the turn, one-shot prompts, inline edits, code completion, classification, summaries, and sub-agents. ONESHOT_JOBS are the jobs that send one prompt and read one answer back.

claude_ctx gives a Claude model’s context window, the number of tokens it can read at once. claude_wire gives the id to ask Claude Code for, which carries a [1m] suffix for the models that have a million-token window.

Probing the machine

Some questions are about this machine: whether a runtime is installed, which models an API key can list, which models a Copilot plan reaches. Each answer takes too long for a model picker to wait on, and changes rarely enough that the last answer is usually still right. probed(key, fn) remembers these answers. Use it for any slow question whose last answer is good enough to show.

  • The first call runs fn() and returns its answer.
  • Later calls return the remembered answer at once. When it is older than ttl seconds, a background thread asks again, and a later call gets the new answer.
  • The answer is also saved to a file under ~/.config/ramabana/probes, so the next run of the program has a value on its first call. Pass disk=False to keep it in memory only.

forget_probes drops every remembered answer, for a refresh button. forget_probes(disk=True) deletes the files too. The hidden test below walks through each case.

Extras

The core install is the agent, its hosts, and the file, code, shell and git tools. Each extra, such as ramabana[search], adds the packages for one more use. installed says whether a module would import, without importing it. need(extra, *mods) returns an empty string when the packages are present, and otherwise the sentence telling the user what to install, so a command that needs an extra can refuse with something useful. Both live in setup, which the console scripts import first because it loads nothing heavy, and are re-exported here.

Azure OpenAI

Azure OpenAI needs AZURE_OPENAI_ENDPOINT, the resource such as https://NAME.openai.azure.com, and AZURE_OPENAI_API_KEY. config.toml’s [azure] table can hold the endpoint instead, as endpoint, and name another env var for the key with api_key_env; the key itself never goes in the file. Setting them chooses nothing: a deployment is used only where you name it, as azure/DEPLOYMENT or in a [model."NAME"] table. azure_base turns whatever form of the endpoint was pasted into the v1 base, dropping a deployment path and an api-version; the v1 API needs neither. azure_ready says whether the endpoint and the key are both there, and is_azure whether a spec goes to Azure.

for u in ('https://r.openai.azure.com', 'r.openai.azure.com/', 'https://r.openai.azure.com/openai/v1/', 'https://r.openai.azure.com/openai/deployments/x/chat/completions?api-version=2024-10-21'):
    test_eq(azure_base(u), 'https://r.openai.azure.com/openai/v1')
test_eq(azure_base('https://apim.azure-api.net/team/openai'), 'https://apim.azure-api.net/team/openai/v1')
assert azure_host('https://r.openai.azure.us/openai/v1') and not azure_host('https://api.openai.com/v1')

register_model

def register_model(
    name, model_id, runtime:NoneType=None, ctx:int=128000, note:str='custom model', **config
):

Add a model name that lasts until this process exits; save_model keeps one on disk.

A name added with register_model is gone after a restart. save_model keeps one in a file, and every application that offers its own names needs the same file, so the file is handled here:

  • save_model(row) checks a row, registers it, and writes it to the file.
  • load_models() reads the file at startup, registers every row that still resolves, and skips the rest.
  • delete_model(name) removes a name from the file and from this process.
  • saved_models() returns the rows on disk.

A row holds name, model_id, runtime and ctx. A row for the remote runtime may also name an endpoint with base_url, vendor_name and api_name, and the environment variable that holds its key with api_key_env. The file never holds a key. path names the application’s own file and defaults to ~/.config/ramabana/models.json.

config.toml can define a model as well as correct one. A [model."NAME"] table with model_id registers NAME for this process, for [jobs], --model and /model, with the same base_url, api_key_env, api_name, vendor_name and runtime a saved alias carries; ctx is another name for max_input_tokens. Listing models

available_models builds the list a model picker shows. Each row names a model this process can actually run. The on-device models appear when their runtime is installed, ollama’s models when its daemon answers, and a vendor’s models only when the credential for it exists. The hosted lists come from provider_models in models. copilot_catalog is the model list for your Copilot plan, which the Copilot server reports and probed remembers for five minutes. A model config.toml defines appears with source config.toml once it can run.

Defaults and context windows

Every default route is a hosted model:

job default model through
turn claude-opus-5-5 Claude Code
subagent claude-sonnet-5-5 Claude Code
oneshot, inline, summary gpt-6-luna a Codex login
completion, classify claude-haiku-5-5 Claude Code

DEFAULT_POLICY leaves turn empty, so that $RAMABANA_MODEL or DFLT_TURN fills it, and leaves inline empty, so that it follows oneshot. A model on this machine runs the turn only when you name it with --model, /model or $RAMABANA_MODEL. Once you do, the other jobs follow the turn onto the machine. DFLT_LOCAL, qwen-4b, is the local model to suggest; it is never a route unless named.

When none of the hosted models for a job can run here, the job moves to DFLT_FALLBACK, Gemma 4 E4B on LiteRT, rather than failing. The turn never moves. Changing models in the middle of a conversation is your decision, not a default.

A local model’s context window is the size Ramabana uses, which can be smaller than the size it was trained with, because a larger window costs memory and time. local_ctx gives that size: $RAMABANA_LOCAL_CTX first, then config.toml’s max_input_tokens for that model and its window.local_ctx, then the table. The engine still caps it at the size the model was trained with. local_window reads the trained size from the model’s own config, for the runtimes that publish it.

Resolving a model

resolve(name) turns a model name into a ModelSpec: the runtime, the model id, the context window, any runtime options, and a note for the user. Every place that needs to run a model calls it, and code further down accepts the ModelSpec rather than resolving the name again. A runtime that is not installed here does not raise: the spec comes back with missing saying which binary or package is absent and how to get it, the same way a missing API key is left for Agent.start to report. missing_runtime(spec) asks the same question live, and Agent.start turns the answer into a failed turn that names a model that does run here, from available_models. resolve raises KeyError with the closest known names for a name it cannot place.

azure/DEPLOYMENT names an Azure OpenAI deployment on the v1 API of azure_endpoint(), with the key in azure_key_env(), through the Responses API. It resolves whether or not the deployment is listed. A deployment named for a model fastllm knows, such as gpt-5.4, gets that model’s window and briefing; any other name gets 128k and a note saying which [model."azure/NAME"] entry corrects it.

A hosted model’s window comes from fastllm’s table, which can be out of date. A [model."NAME"] table in config.toml corrects it on this machine: max_input_tokens replaces the window, max_output_tokens becomes the reply cap the chat is started with, and supports_images answers accepts(spec, 'image'). The route name you chose the model by wins over its model id.

spec_caps and accepts say what a resolved model can be sent, such as images or audio. A model rishi knows nothing about counts as accepting everything. model_note describes a spec in one line for a status bar.

What a model can afford

Before a turn, the agent sends the model a briefing: the system prompt with the project’s rules, the tool schemas, and sometimes the full text of a skill. On a small context window this fills most of the space before any work starts. On a full host the tool schemas cost about 4.7k tokens, an inlined skill 3k more, and the briefing 1.4k, which leaves a 16k model room for about one tool result.

budget_for(spec, tool_max) sizes the briefing to the model’s window and returns a Budget. For a window above 24k tokens the budget changes nothing except the cap on each tool result. For a smaller window it drops the memory and web tool groups, stops inlining skill text, and clips each tool result harder. It only holds things back: a skill it does not inline is still one read_skill call away. With channel='tags' it first subtracts the tokens the tool schemas will take inside the prompt (see below).

Where the tool schemas travel

A tool schema tells the model what a tool is called and what arguments it takes. There are two ways to send them. The native channel uses the model API’s own tool field: the API checks the schemas, and tool calls come back as structured data. The tags channel, rishi’s tool_mode='tags', writes the schemas into the system prompt and reads tool calls back out of the reply text, written as Hermes-style tags. The local engines have always worked this way, which is why parse_tool_tags exists.

Native is better wherever it is open, but it is not always open. Claude Code receives tools as an in-process MCP server, and a company-managed Claude Code configuration can forbid every MCP server it did not approve. Without the tags channel, that policy would leave the agent unable to read a file. Rishi uses the native channel for Claude Code where its SDK can, and tags in the CLI or wherever the server is refused.

tool_channel(spec, chat) returns 'native' or 'tags'. It is the one place that picks. $RAMABANA_TOOL_CHANNEL overrides everything. Otherwise it asks the open chat, which knows which channel it ended up on, and without a chat it predicts from the spec: tags for Claude Code, and tags for a model that force_tags marked because a request refused its schemas. forget_forced_tags clears those marks so the native channel is tried again. budget_for takes the channel as an argument because the schemas cost prompt tokens on the tags channel.

Routing

Routing decides which model runs each job. It is the only place that does. Build one with the turn model you want, or leave it out to use $RAMABANA_MODEL, then turn in config.toml’s [jobs], then DFLT_TURN. name_for(job) gives the model name for a job, and spec(job) resolves it to a ModelSpec ready to run. To give one job a model of its own, set $RAMABANA_MODEL_<JOB>, name it in config.toml’s [jobs] (the env var wins), call set(name, job), or type /model JOB NAME in a session. A job with no entry in the policy uses the turn’s model, so adding a job to JOBS never leaves a caller with nothing.

When the turn runs on this machine, every job without a model of its own stays on it too, sub-agents included, so nothing leaves the machine.

When a job’s model cannot run here, spec moves the job to another hosted route it already knows, and never to a local model nobody named. When claude-haiku-5-5 cannot run, it tries claude-sonnet-5-5 first. alternatives(job) lists the routes in the order they are tried, ending with DFLT_FALLBACK. A hosted model whose key is missing counts as one that cannot run, for every job but the turn; the turn’s missing key is reported by Agent.start. A model whose answer failed or came back empty is set aside for DOWN_TTL, five minutes. Each move is written to notes, keyed by job, and news holds one line per model that fell, for the chat to show once. When no route is left, the error names the job, the model, and the key or command it needs. missing_key and needs build that part of the message.

A machine with no Claude Code and no Codex login cannot run the defaults, and nothing is chosen in their place: Ramabana asks for a provider instead. PROVIDERS lists the ones it can use and what each needs, provider_ready says which are set up here, and needs_setup(routing) says why the turn’s model cannot run, a missing runtime or a missing key, or nothing. setup_guide puts it together for a person: the providers, then each job, the model it runs on, where that was chosen (job_source: an env var, config.toml, the turn it follows, or the default) and whether it can run. The terminal prints it before a session whose turn cannot run, and ramabana setup adds a provider.

AWS Bedrock is reached through its OpenAI-compatible Mantle endpoint, https://bedrock-mantle.<region>.api.aws/v1, with a Bedrock API key in AWS_BEARER_TOKEN_BEDROCK sent as a bearer token; such keys are often short-lived, so renew them as AWS says. Model ids are Bedrock’s own, such as openai.gpt-5.4, and their windows come from fastllm’s bedrock_mantle table. Bedrock’s native Converse and InvokeModel APIs, and with them Claude on Bedrock, are not supported: fastllm has no SigV4 signing, no AWS credential chain or profile, and no Converse wire format.

image_route is the image job, which generate_image draws with: $RAMABANA_MODEL_IMAGE, config.toml’s [jobs] image, or DFLT_IMAGE, OpenAI’s gpt-image-1. It gives the endpoint, key and model of an OpenAI-shaped images API, such as an Azure deployment of gpt-image-1, or a sentence saying what to set up; Bedrock’s Mantle endpoint and OpenRouter have no images endpoint.

video_route is the video job in the same way: $RAMABANA_MODEL_VIDEO, config.toml’s [jobs] video, or DFLT_VIDEO, Google’s Veo 3. It gives api, gemini for Gemini’s long-running predictLongRunning API or openai for an OpenAI-shaped /videos API such as sora-2 on OpenAI or Azure, with the endpoint, key and model id. A model fastllm knows to return no video is refused, as is a local model or a host with no video endpoint, and each refusal says what to set up. video_route(name) resolves one named model, so a job started earlier is polled with the key it was started with.
