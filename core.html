core

Shared errors, environment settings, and the rules that decide which model runs each job.

Errors and environment

Ramabana reports a failure in one of two ways. AgentError is a refusal: an action Ramabana declines to perform, with a message the user can act on. Examples are a write outside the open folders and a model whose key is missing. AgentError is shalya’s HostError under another name. One except clause catches a refusal from a tool and a refusal from the agent. Any other exception is a bug and propagates as one.

ContextFull is the refusal raised when a turn does not fit the model’s window after compaction and trimming.

BranchChanged is the refusal raised when a git branch moved while a person was deciding whether to approve a write to it. Nothing was written.

The model tables

MODELS is the table of short model names you can type, such as sonnet or gemma-e4b. Each name maps to a pair: the runtime that serves the model, and the id that runtime knows the model by. Smaller tables make up MODELS. LOCAL holds the LiteRT models, MLX the models for Apple silicon, LLAMA the llama.cpp models, CLOUD the OpenAI and Codex models, and the Claude tables come from the catalog in models.

JOBS lists every job the policy can route on its own: the turn, one-shot prompts, inline edits, code completion, classification, summaries, and sub-agents. ONESHOT_JOBS are the jobs that send one prompt and read one answer back.

claude_ctx returns a Claude model’s context window, the number of tokens it can read at once. It returns DFLT_AGENT_CTX (128,000) for an id that no entry of CLAUDE_CTX matches. claude_wire returns the id to ask Claude Code for. The id has a [1m] suffix for a model with a million-token window.

Probing the machine

Some questions are about this machine: whether a runtime is installed, which models an API key can list, which models a Copilot plan reaches. Each answer is too slow for a model picker to wait on. Each answer changes rarely. probed(key, fn) remembers these answers. Use it for a slow question whose last answer is good enough to show.

  • The first call runs fn() and returns its answer.
  • Later calls return the remembered answer at once. When the answer is older than ttl seconds (PROBE_TTL, 90 by default), a background thread calls fn() again. A later call returns the new answer. When the background call raises, the old answer stays and the next refresh waits another ttl seconds.
  • probed also saves the answer to a file under ~/.config/ramabana/probes. The next run of the program then has a value on its first call, and refreshes it in the background. Pass disk=False to keep the answer in memory only.

forget_probes drops every remembered answer. Call it from a refresh button. forget_probes(disk=True) deletes the files too. The hidden test below walks through each case.

Extras

The core install is the agent, its hosts, and the file, code, shell and git tools. Each extra, such as ramabana[search], adds the packages for one more use. installed says whether a module would import, without importing it. need(extra, *mods) returns an empty string when the packages are present. Otherwise it returns a sentence that tells the user what to install. A command that needs an extra can refuse with that sentence. Both functions are defined in setup and re-exported here. The console scripts import setup first because it loads nothing heavy.

Azure OpenAI

Azure OpenAI needs AZURE_OPENAI_ENDPOINT, the resource such as https://NAME.openai.azure.com, and AZURE_OPENAI_API_KEY. config.toml’s [azure] table can hold the endpoint instead, as endpoint. It can also name another env var for the key with api_key_env. The key itself never goes in the file. Setting the endpoint and key does not select a deployment. Ramabana uses a deployment only where you name it, as azure/DEPLOYMENT or in a [model."NAME"] table. azure_base converts any form of the endpoint to the v1 base. It drops a deployment path and an api-version, which the v1 API does not use. azure_ready returns whether the endpoint and the key are both set. is_azure returns whether a spec goes to Azure.

for u in ('https://r.openai.azure.com', 'r.openai.azure.com/', 'https://r.openai.azure.com/openai/v1/', 'https://r.openai.azure.com/openai/deployments/x/chat/completions?api-version=2024-10-21'):
    test_eq(azure_base(u), 'https://r.openai.azure.com/openai/v1')
test_eq(azure_base('https://apim.azure-api.net/team/openai'), 'https://apim.azure-api.net/team/openai/v1')
assert azure_host('https://r.openai.azure.us/openai/v1') and not azure_host('https://api.openai.com/v1')

register_model

def register_model(
    name, model_id, runtime:NoneType=None, ctx:int=128000, note:str='custom model', **config
):

Add a model name until this process exits. save_model keeps a name on disk.

A name added with register_model is gone after a restart. save_model keeps a name in a file. Every application that offers its own model names needs this file, and this module manages it:

  • save_model(row) checks a row, registers it, and writes it to the file.
  • load_models() reads the file at startup, registers every row that still resolves, and skips the rest.
  • delete_model(name) removes a name from the file and from this process.
  • saved_models() returns the rows on disk.

A row holds name, model_id, runtime and ctx. A row for the remote runtime can also have base_url, vendor_name and api_name to name an endpoint, and api_key_env to name the environment variable that holds its key. The file never holds a key. Each function takes a path for the application’s own file. path defaults to ~/.config/ramabana/models.json, or to the file that use_aliases set.

config.toml can define a model as well as correct one. A [model."NAME"] table with model_id registers NAME for this process, for [jobs], --model and /model, with the same base_url, api_key_env, api_name, vendor_name and runtime keys that a saved alias has. ctx is another name for max_input_tokens. A name defined in both places belongs to config.toml. load_models skips it and save_model refuses it. An application with its own alias file calls use_aliases(path) to make that file the default for calls that name no file.

remote_models() lists the hosted models whose credentials are set. It covers models defined in config.toml and saved aliases, config.toml’s first. A setup page counts them. The routing never picks one of them by itself.

Listing models

available_models builds the list a model picker shows. Each row names a model this process can actually run. The on-device models appear when their runtime is installed, ollama’s models when its daemon answers, and a vendor’s models only when the credential for it exists. The hosted lists come from provider_models in models. copilot_catalog is the model list for your Copilot plan, which the Copilot server reports and probed remembers for five minutes. A model config.toml defines appears with source config.toml once it can run.

Models selectable here, with older generations only when include_legacy. With ttl, the last answer within ttl seconds: an older one comes back at once and is asked again in the background, and the answer is kept on disk for the next run.

Each row has a value to pass to resolve, a label to show, its provider, and the source that made it available. The picker shows the source beside the label. This check fakes a Copilot plan with one chat model:

Each row also says whether the model runs on this machine (local) and the model_id its value resolves to. The slow probes start together: ollama’s list, Copilot’s catalogue, the Claude Code sign-in and each vendor’s live list. A settings page that opens often passes ttl: a call within ttl seconds asks nothing, an older answer comes back at once and is asked again in the background, and a new process starts from the answer on disk. Without ttl each call asks again.

r = available_models()[0]
test_eq({'local', 'model_id'} <= set(r), True)
test_eq(available_models(ttl=60), available_models(ttl=60))

Older model generations, such as gpt-4.1, are left out unless you ask for them with include_legacy=True:

names = {r['value'] for r in available_models()}

test_eq(names - legacy, set())
sorted(legacy - names)
['openai/gpt-4.1', 'openai/gpt-4.1-mini', 'openai/gpt-4.1-nano']

Defaults and context windows

Every default route is a hosted model:

job default model through
turn claude-opus-5-5 Claude Code
subagent claude-sonnet-5-5 Claude Code
oneshot, inline, summary gpt-6-luna a Codex login
completion, classify claude-haiku-5-5 Claude Code

DEFAULT_POLICY leaves turn empty. $RAMABANA_MODEL or DFLT_TURN fills it. It also leaves inline empty, and inline follows oneshot. A model on this machine runs the turn only when you name it with --model, /model or $RAMABANA_MODEL. Once you do, the other jobs follow the turn onto the machine. DFLT_LOCAL, qwen-4b, is the local model to suggest. It is never a route unless named.

When none of the hosted models for a job can run here, the job moves to DFLT_FALLBACK, Gemma 4 E4B on LiteRT, rather than failing. The turn never moves. Changing models in the middle of a conversation is your decision, not a default.

A local model’s context window is the size Ramabana uses. It can be smaller than the size the model was trained with. A larger window costs memory and time. local_ctx returns that size from the first of these that sets one: $RAMABANA_LOCAL_CTX, config.toml’s max_input_tokens for that model, config.toml’s window.local_ctx, then the built-in table. The engine still caps the size at the size the model was trained with. local_window reads the trained size from the model’s own config, for the runtimes that publish it.

Resolving a model

resolve(name) turns a model name into a ModelSpec: the runtime, the model id, the context window, any runtime options, and a note for the user. Every place that needs to run a model calls it. Code further down accepts the ModelSpec and does not resolve the name again. A runtime that is not installed here does not raise. The spec comes back with missing set to the binary or package that is absent and how to get it. A missing API key works the same way: Agent.start reports it. missing_runtime(spec) asks the same question live. Agent.start turns the answer into a failed turn that names a model from available_models that does run here. resolve raises KeyError with the closest known names for a name it cannot place.

azure/DEPLOYMENT names an Azure OpenAI deployment on the v1 API of azure_endpoint(), with the key in azure_key_env(), through the Responses API. It resolves whether or not the deployment is listed. A deployment named for a model fastllm knows, such as gpt-5.4, gets that model’s window and briefing. Any other name gets 128k and a note that names the [model."azure/NAME"] entry that corrects it.

A hosted model’s window comes from fastllm’s table, which can be out of date. A [model."NAME"] table in config.toml corrects it on this machine. max_input_tokens replaces the window. max_output_tokens sets the reply cap that the chat starts with. supports_images answers accepts(spec, 'image'). The table for the route name you chose the model by wins over the table for its model id.

spec_caps and accepts say what a resolved model can be sent, such as images or audio. A model rishi knows nothing about counts as accepting everything. model_note describes a spec in one line for a status bar.

Copilot needs its own runtime. Suppose remote received copilot/gpt-5.5. rishi would read copilot as a prefix it knows and drop it. It would send the bare gpt-5.5 to OpenAI with your OpenAI key. The turn would work, and OpenAI would bill the wrong account. resolve therefore handles the copilot/ prefix itself. It reads the Copilot model list from the Copilot server instead of a table. The list depends on the plan and changes often. Each entry carries the context window that Copilot allows:

_cat = {'gpt-5.5': {'capabilities': {'type': 'chat', 'limits': {'max_prompt_tokens': 272000}}},
        'claude-opus-4.7': {'capabilities': {'type': 'chat', 'limits': {'max_context_window_tokens': 264000}}},
        'text-embedding-3-small': {'capabilities': {'type': 'embeddings'}}}
_orig_avail, _orig_cat = _copilot_available, copilot_catalog

What a model can afford

Before a turn, the agent sends the model a briefing: the system prompt with the project’s rules, the tool schemas, and sometimes the full text of a skill. On a small context window this fills most of the space before any work starts. On a full host the tool schemas cost about 4.7k tokens, an inlined skill 3k more, and the briefing 1.4k, which leaves a 16k model room for about one tool result.

budget_for(spec, tool_max) sizes the briefing to the model’s window and returns a Budget. For a window above 24k tokens the budget changes nothing except the cap on each tool result. For a smaller window it drops the memory and web tool groups, stops inlining skill text, and clips each tool result harder. It only holds things back: a skill it does not inline is still one read_skill call away. With channel='tags' it first subtracts the tokens the tool schemas will take inside the prompt (see below).

Where the tool schemas travel

A tool schema tells the model what a tool is called and what arguments it takes. There are two ways to send them. The native channel uses the model API’s own tool field: the API checks the schemas, and tool calls come back as structured data. The tags channel, rishi’s tool_mode='tags', writes the schemas into the system prompt and reads tool calls back out of the reply text, written as Hermes-style tags. The local engines have always worked this way. urai provides parse_tool_tags for it.

Native is better wherever it is open. It is not always open. Claude Code receives tools as an in-process MCP server. A company-managed Claude Code configuration can forbid every MCP server it did not approve. Without the tags channel, that policy leaves the agent unable to read a file. rishi uses the native channel for Claude Code where its SDK can, and tags in the CLI or wherever the server is refused.

tool_channel(spec, chat=None, scope='turn', session='') returns 'native' or 'tags'. Nothing else picks the channel. A local engine takes no tool_mode, and tool_channel always returns native for it. For any other runtime, tool_channel uses the first of these that sets a channel:

  1. $RAMABANA_TOOL_CHANNEL.
  2. tags, for a model that force_tags marked because a request refused its schemas.
  3. The session’s choice: /model tools for the turn, /subagents tools for sub-agents.
  4. config.toml’s [model."NAME"] tool_channel.
  5. The scope’s own key: runtime.tool_channel, or for sub-agents $RAMABANA_SUBAGENT_TOOL_CHANNEL and then subagents.tool_channel. A sub-agent falls back to runtime.tool_channel.
  6. The runtime’s default: tags for Claude Code, native for the rest.

A person can write text for tags. tool_channel never asks the open chat, because a replayed chat has no such attribute. Native for Claude Code needs a rishi that carries tools through its in-process MCP server. With an older rishi the answer stays tags. forget_forced_tags clears the marks, and the native channel is tried again. budget_for takes the channel as an argument because the schemas cost prompt tokens on the tags channel.

Routing

Routing decides which model runs each job. Nothing else decides. Build one with the turn model you want. Without an argument, the turn model is $RAMABANA_MODEL, then turn in config.toml’s [jobs], then DFLT_TURN. name_for(job) returns the model name for a job. spec(job) resolves that name to a ModelSpec ready to run. Four actions give one job a model of its own: set $RAMABANA_MODEL_<JOB>, name the job in config.toml’s [jobs] (the env var wins), call set(name, job), or type /model JOB NAME in a session. A job with no entry in the policy uses the turn’s model. A job added to JOBS always has a model.

When the turn runs on this machine, every job without a model of its own stays on it, sub-agents included. A job with a model of its own can run on a hosted model.

When a job’s model cannot run here, spec moves the job to another hosted route that the policy already names. spec never moves a job to a local model that nobody named, except the last resort DFLT_FALLBACK. A job with no model of its own goes to the turn’s model first. That move is the plan and writes no note. One model that runs is enough for every job. A job that someone gave claude-haiku-5-5 tries claude-sonnet-5-5 first. alternatives(job) lists the routes in the order spec tries them, ending with DFLT_FALLBACK. A job that follows a local turn has no alternatives. A hosted model whose key is missing counts as a model that cannot run, for every job but the turn. Agent.start reports the turn’s missing key. A model whose answer failed or came back empty is set aside for DOWN_TTL, five minutes. spec writes each move to notes, keyed by job. news holds one line per model that fell, for the chat to show once. When no route is left, the error names the job, the model, and the key or command it needs. missing_key and needs build that part of the message.

A machine with no Claude Code login cannot run DFLT_TURN. Building a Routing never changes its turn. Suppose nobody named the turn for this run, with turn= (the --model flag), set or $RAMABANA_MODEL, and its model cannot run here. Then settled() names where the turn should go: ready_turn(), the first provider in READY_ORDER that is ready, subscriptions before keys. Agent.settle moves the turn there once, when a session starts. Ramabana never replaces a turn named for this run. Ramabana never picks Azure, Bedrock or a custom endpoint, because each needs a name only its owner knows.

PROVIDERS lists the providers Ramabana can use and what each needs. provider_ready says which providers are set up here. needs_setup(routing) returns why the turn’s model cannot run here: a missing runtime, a missing key, or a Claude Code that nobody signed in to. It returns an empty string when the model can run. setup_guide formats this for a person: the providers, then each job with the model it runs on, where that model was chosen, and whether it can run. job_source names the origin: env, config.toml, chosen (a set call), follows the turn or default. A one-shot or piped run whose turn cannot run prints the guide and exits. An interactive session opens anyway, on welcome(routing), which says why nothing runs and lists the commands that fix it. ramabana setup adds a provider from a shell.

AWS Bedrock is reached through its OpenAI-compatible Mantle endpoint, https://bedrock-mantle.<region>.api.aws/v1, with a Bedrock API key in AWS_BEARER_TOKEN_BEDROCK that goes out as a bearer token. Bedrock API keys can be short-lived. Renew them as AWS instructs. Model ids are Bedrock’s own, such as openai.gpt-5.4, and their windows come from fastllm’s bedrock_mantle table. Ramabana does not support Bedrock’s native Converse and InvokeModel APIs, and so does not support Claude on Bedrock. fastllm has no SigV4 signing, no AWS credential chain or profile, and no Converse wire format.

image_route resolves the image job, which generate_image uses. The model comes from $RAMABANA_MODEL_IMAGE, config.toml’s [jobs] image, or DFLT_IMAGE, OpenAI’s gpt-image-2.5-sunburst. image_route returns the endpoint, key and model of an OpenAI-shaped images API, such as an Azure deployment of gpt-image-2.5-sunburst. When no such API is usable, it returns a sentence that says what to set up. Bedrock’s Mantle endpoint and OpenRouter have no images endpoint.

video_route resolves the video job the same way, from $RAMABANA_MODEL_VIDEO, config.toml’s [jobs] video, or DFLT_VIDEO, Google’s Veo 3. It returns api, the endpoint, the key and the model id. api is gemini for Gemini’s long-running predictLongRunning API, or openai for an OpenAI-shaped /videos API such as sora-2 on OpenAI or Azure. video_route refuses a model that fastllm knows to return no video, a local model, and a host with no video endpoint. Each refusal says what to set up. video_route(name) resolves one named model. A job started earlier is then polled with the key it started with.
