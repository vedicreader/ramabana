Ramabana in a terminal: a transcript of blocks, a status bar, and one line to type in.

Two small fixes to teleprint are applied when this module loads. Each checks whether the installed teleprint already has the fix and does nothing if so; FRAME_PATCHED and INK_PATCHED record whether the patch was needed.

The first concerns rows already written to the scrollback. Teleprint keeps a mark, _ws, of how many rows of the document it has committed there, and each frame writes only the rows past the mark. Those rows are history in the terminal and cannot be taken back. When a tool result folds, the document gets shorter, and teleprint used to lower the mark to match, so the next frame wrote earlier rows a second time. A session with many folded calls ended up with many copies of its startup banner. The patch keeps the mark from ever going down.

The second adds a hook, Compositor.on_frame, which runs after each paint. Pictures need it: a picture is placed on the screen after the text is drawn, as the section on pictures below explains. The hook is installed before the mark fix, so _frame.__wrapped__ is the frame without the mark fix, and the test below uses it to show the duplicated rows.

Ramabana gives shift+enter its own meaning: during a turn it queues the line as the next turn, where plain enter steers the running one. By default a terminal sends the same byte for both keys, so the program has to ask the terminal for richer key reports. There are two protocols for this:

  • Kitty’s keyboard protocol, with flag 1 (“disambiguate”), reports a modified key as CSI code;mods u. Ghostty and kitty support it.
  • Xterm’s modifyOtherKeys, at level 1, reports it as CSI 27;mods;code ~. Tmux sends this form when its extended-keys option is on, and the kitty form when extended-keys-format is csi-u.

The compositor asks for both, and each terminal answers with the one it supports. ext_key turns either report into the same Key the old byte parser would have produced. Once kitty’s flag is on, esc, control letters and alt letters also arrive in the new form, so the decoder has to cover every key, and it follows these rules:

  • A key release is dropped.
  • Keypad keys decode to the same characters and names the old bytes gave.
  • ctrl+i, ctrl+j and ctrl+m stay tab and enter.
  • Kitty’s other private-use keys, such as bare modifiers and media keys, are dropped rather than typed.
  • Caps lock and num lock are ignored, since they are states rather than key chords.
  • Chords with super, hyper or meta have no names here and are dropped.

ext_keys_ok decides whether to ask at all: only when both stdin and stdout are a real terminal, so tests and pipes never see the escape codes. The compositor turns the modes off wherever it hands the terminal back: at stop, at release when another program borrows the terminal, before a fatal signal, and while ctrl+z has the process suspended. A ctrl+z from the transcript view also leaves the alternate screen while suspended and comes back on fg. Kitty keeps a separate flag stack for the alternate screen, so the transcript view sets the flag again there and clears it before leaving.

Blocks and keys

Every block has a kind, and each kind has its own gutter, the mark in the left margin. GUTTERS maps the nine kinds to their marks: user for your prompts (▌), step for the agent’s narration (┆), tool for a tool call (│), reply for the answer, ask for an approval question (◆), plan for the plan checklist (▸), note for a message from Ramabana itself (·), error (×), and media for a picture.

A turn is one prompt and everything the agent does to answer it. In the transcript it reads as a timeline in the order the work happened: a step for each stretch of narration, a tool block for each call that narration introduced, and one reply with the answer at the end. Results fold to one row and narration stays visible, so the answer always sits below the narration that led to it.

Attachments

A prompt can carry files with it: pictures, sound, or text. In the terminal you attach one in three ways. You can drop the file on the window, paste its path, or write @path in the prompt. All three end up as the same attachment. The path parser accepts quoted paths, paths in brackets, file:// URIs and backslash-escaped spaces, and a plain sentence that merely mentions a path is left alone, as the tests below check.

A picture goes to the model as an image content part, the form a model API takes images in. Every attachment also carries its absolute path, and the path still works when the model cannot take the content part. A model without audio support, for example, can still open a .wav through the file tools.

The attachment helpers themselves, media_paths, Attachment, media_parts and the rest, live in ramabana.tools and are imported here so the terminal and the other frontends share one parser.

Pictures, drawn where the terminal can draw

A picture can reach the screen in two ways. The model can return one in Resp.media, or a tool can write an image file during the turn and report it through on_media. On a terminal without kitty graphics, the picture is saved and its path printed. kitty_graphics decides which kind of terminal this is, from the environment variables and $TERM names in KITTY_ENV and KITTY_TERM.

On a terminal with kitty graphics the picture is drawn in place. Kitty positions an image by screen cell, separately from the text. The compositor redraws its document with absolute cursor moves, so an image cannot ride along in the text the way prose does. A Picture handles this in two steps. Picture.send transfers the image bytes to the terminal once. The block itself holds only the blank rows the picture will cover, sized by img_cells from png_size. Then Picture.place writes a short placement command at the end of every frame, at the current position of those blank rows. Each placement reuses the picture’s image id, which replaces the previous placement, so repaints never stack copies. If the terminal clears the cells under an image, the next frame places it again.

picture builds a Picture for a file, or returns None when this terminal or this file cannot be drawn. draw_png is for code that has no frames to hook into: it sends and places a picture at the cursor in one go. media_line is the transcript line for a saved picture.

Kitty also offers Unicode placeholders, where the image is anchored to special characters in the text. They are not used, because Kaku and at least one other terminal ignore the U=1 flag, draw at the cursor, and print U+10EEEE as a missing glyph, which leaves a block of boxes behind the picture.

The turn

A turn starts when you press enter on a prompt. run_turn runs one turn and streams it into the transcript. The agent’s agent.stream is a blocking generator that runs on a separate model thread, so run_turn reads its chunks from a queue. That keeps the event loop free to handle keystrokes, approval questions and activity updates while the model works.

Before the turn starts, some prompts get a row of choices. A request such as “refactor the runtime” can mean “make the change”, “propose a plan”, or “say what is in scope”, and learning which one the model picked is costly. options_for checks the typed line against the trigger words in MENUS and returns a title and a list of Options, or None. ChoiceMenu draws the row above the input line and handles the keys that move through it and pick one. Each Option carries the instruction it appends to the prompt (its suffix), so the choice reaches the model as part of what you asked for. The REFACTOR options are the only menu at present. The examples of the menu in use come later, under the surface.

close_done_shells closes the tmux panes of run_shell_bg commands that have finished; their output stays readable through cmd_output.

The surface

Ui is the whole terminal surface, and the class the rest of this page builds on. It has three jobs. It paints the tail, the status bar and input line at the bottom of the screen. It turns tool calls and approval requests into blocks. And it decides what each keystroke means: on_key returns a coroutine for the caller to start (a turn, for example), the string 'quit', or None when the key was handled.

Every method on Ui is synchronous and does no terminal I/O of its own, so the examples below drive it against an emulated terminal with no mocks. The one care it takes is with threads. Activity and approval callbacks arrive on the model’s worker thread, and only the event loop thread may touch the compositor, so those callbacks are handed to the loop through _post.

The class is long, and later cells add to it with fastcore’s @patch. The methods a caller is most likely to use are submit for the typed line, say to print a block, note for a one-line message, stream for reply text as it arrives, and paint to redraw.

A line starting with /name that is not one of the agent’s slash commands is looked up as a skill or a command file. Command files are markdown files in <cfg>/commands/*.md, plus a root’s .agents/commands/ once the project_extensions option is turned on. So /exhash fix the loop sends the prompt “fix the loop” with the exhash skill attached, instead of reporting an unknown command. In a command file, $ARGUMENTS is replaced by everything after the name, $1 to $n by its separate words, and each @path by that file when it lies inside the open folders. A command file with subtask: true in its frontmatter is sent as a task for delegate_async, which runs it in a sub-agent.

The approval keys come next. While an approval question waits, y approves, n refuses, and lowercase a approves this request and everything else for the rest of the session. Capital A approves and also adds a rule that always allows requests like this one, through always_allow, when the approval gate can hold rules; ask_pattern is what that rule matches. Without rules, A behaves like a. parse_answer reads a typed answer such as y, no or n: put it in docs/.

A waiting question rings the terminal bell with ring, but only once nobody has typed for BELL_IDLE seconds. nudge shows the question again every REASK_EVERY seconds while it waits, and reask does the showing. #note TEXT at the prompt calls note_memory, which keeps the line for the next session’s memory.

Python mode

Python mode gives the same prompt a second meaning. /python starts a Jupyter kernel that belongs to you, and from then on a line you type runs as Python in that kernel. /agent hands the line back to the model and leaves the kernel running; only /quit or the end of the process shuts it down. Everything else stays the same: the transcript, folding, approvals, attachments and slash commands. Only what enter does with the line changes.

The agent follows you into the kernel. enter_python points the agent’s Python tools at a Dhrishti overlay on the new kernel. An overlay is a layer over your namespace: the agent can read every name you defined and writes its own names into its layer, and it cannot rebind a name you made. The host stays the same object. enter_python then calls Agent.refresh, which drops the cached skills, registry and tools and gives the running model backend a fresh briefing with the new tools.

Related methods: run_code runs one cell you typed and prints its outputs as blocks, complete_python handles tab completion from the kernel, attach_session points the agent at someone else’s live Dhrishti session for --attach, and enable_agent_proxy makes this session’s agent callable from the Python prompt for --agent-proxy. /promote NAME copies one of the agent’s variables into your namespace.

pyrepl holds the parts that judge Python: the kernel, the overlay host, whether a line compiles, and how to colour it. It is imported only when Python mode starts, so a plain ramabana session needs no kernel. The tests that need a live kernel are on that page.

Shell lines

A line that starts with ! runs as a shell command in the first open folder, with no approval question, because you typed it yourself. run_shell_line runs it. Its output prints as one block, followed by the exit code, and a non-zero exit code prints as an error. The model never sees the command or its output.

So that the model knows this exists, main adds SHELL_NOTE to an interactive session’s extra_sp, the extra text appended to the agent’s briefing, before a resumed session builds its briefing. The note tells the model it can ask you to run a command with !. A one-turn run from the command line never gets the note. ! lines work only in agent mode; in Python mode the line is Python, and code_state rejects it because it does not compile.

The command runs in its own process group with stdin from /dev/null, so a command that tries to read from the terminal gets end of file instead of hanging. Ui.shell_proc holds the process while it runs, which is how ctrl+c reaches it (see stop further down).

Folding

A block taller than FOLD (12 rows) starts folded, so a four-hundred-line result takes one row until you open it. ctrl+o opens all the working of the latest turn, every step and call, and a second press folds it again. alt+o does the same for every turn, and alt+1 to alt+9 open a single entry, newest first. The main screen leaves the mouse to the terminal, so selecting and copying work as in any scrollback. In the transcript view, a block opens and closes under the block cursor or with a click.

comp.toggle(long)
long.collapsed

A one-line block has nothing to fold, so toggling it does nothing and raises no error.

comp.toggle(short), short.collapsed

A tool call folds to its own summary line rather than at FOLD rows, because the summary is what you want to read. A turn of thirty calls reads as thirty lines, and any one result is a keystroke away.

The fold is decided when the result arrives. A tool block is printed when the call starts, one hourglass row tall, and the result is put into the same block when the call returns. Teleprint’s print_block decides folding once, from the height at print time, which would be 1, so on its own it would leave every result open. _act therefore decides the fold again at the moment the result lands.

A delegation, where the agent hands a question to a sub-agent, shows as one entry with the sub-agent’s calls grouped under it. A sub-agent is a second agent the main one starts for a piece of work, here through delegate_search. It runs on the same recorded tool wrappers as its caller, so its calls arrive in the same Activity feed. Each of them carries a parent_action_id, which Agent sets from a per-thread stack of the delegate calls in flight, and Ui uses it to put the call under its parent. Without the grouping, the searches of three sub-agents would appear among the caller’s own calls.

A finished call folds to its summary, unless it is a write or a diff (see opens above). Copying and browsing

There are two ways to copy out of the transcript, and both use the system clipboard. On the main screen the mouse belongs to the terminal, so you select and copy as in any scrollback. The transcript view, opened with ctrl+r or up, takes the mouse only while it is open (enter_transcript and leave_transcript). /copy and the view’s y key send the text over OSC 52, a terminal escape code for setting the clipboard, which works through ssh and tmux.

They copy a block’s source text rather than what is drawn: the Markdown the model wrote, or the arguments a tool got. Running it

mk_agent from ramabana.agent builds what the terminal runs. It makes a WorkspaceHost over the folders named on the command line, an Agent over that host, and an approval gate connected to both. A host is the object that supplies the agent’s tools and decides what they may touch: which folders, whether the network is reachable, and which writes need approval. mk_host builds the host alone. amain is the terminal loop that runs the Ui, and it stays short because the behaviour lives in Ui.

The prompt appears before the model is ready. begin builds the system prompt and tools and starts the model on a thread, and the status bar says starting model… meanwhile. A line sent before the model is up waits in the queue, like a line sent during a turn, and runs once the model is ready.

start_agent starts the turn model and then the code index, the search index behind search_code, so the index never delays the model. sync_index decides whether the index needs rebuilding: it rebuilds when a package or an open folder changed since the last good build, otherwise reopens the saved index, and logs which it did to <cfg>/kosha.log. warm_up runs start_agent off the loop with off_loop, and prints a note saying why when no model starts.

amain is the interactive loop: one terminal, one event loop, and one owner of the keyboard. It starts the compositor, connects keys, pastes, resizes and mouse events to the Ui, starts the model with begin, opens Python mode when asked, and on exit restores the terminal and shuts down the agent and any kernel.

Three helpers keep a broken terminal from breaking the session. AppTty is teleprint’s RealTty with one change: when the terminal hangs up, reading stops and writes are dropped, so the session quits instead of spinning. stderr_to sends Python’s stderr to a file while the screen belongs to the compositor, because a warning written straight to the terminal would scroll the transcript under the compositor’s frames; it also points faulthandler at that file so a hard crash leaves its stack trace there. stderr_log names the file, inside the session’s own run folder.

Ui.stop

def stop():

Escalate repeated Ctrl-C from cancellation to termination to exit.

stop is what ctrl+c does, and repeated presses escalate. During a turn, the first press cancels the turn’s run, the second terminates it, and the third quits; presses count as repeats only while they come within the agent’s cancel_grace seconds of each other. Each press also takes queued lines back into the composer, so nothing you typed is lost.

For a ! command, stop signals the command’s process group. The first ctrl+c sends SIGINT, and the next sends SIGKILL, however long after the first it comes. A command ended by a signal prints stopped, and the prompt is free once the process exits. Quitting kills a command that is still running.

on_key is patched once more so that ctrl+c stops a turn without clearing the composer, and alt+up pulls queued text back into the composer for editing.

The now pane

The now pane is a small live view, in a tmux split beside the chat, of what the main agent and each sub-agent are doing at this moment: the turn, the call it is on, and each sub-agent run with its own calls. The surface writes a snapshot, now_snapshot, to <runs_dir>/now.json from its own loop: at most every PANE_EVERY seconds while calls change or a turn runs, and once more when the turn ends. ramabana-pane, from pane, reads that file and draws it.

  • /pane opens it with open_pane and /pane off closes it with close_pane.
  • --pane auto|on|off decides whether a session starts with it, through start_pane; auto opens it only inside tmux.
  • pane_cmd is the shell line that runs the viewer for a given file.

When the viewer crashes rather than quits, the surface reopens it, a limited number of times.
