Ramabana in a terminal: a transcript of blocks, a status bar, and one line to type in.

This module applies two small fixes to teleprint when it loads. Each fix checks whether the installed teleprint already has it and does nothing if so. FRAME_PATCHED and INK_PATCHED are True when the module applied the fix.

The first fix concerns rows already written to the scrollback. Teleprint keeps a mark, _ws, of how many rows of the document it has committed to the scrollback. Each frame writes only the rows past the mark. Those rows are history in the terminal and cannot be taken back. When a tool result folds, the document gets shorter. Teleprint used to lower the mark to match, and the next frame wrote earlier rows a second time. A session with many folded calls had many copies of its startup banner. The fix never lets the mark go down.

The second fix adds a hook, Compositor.on_frame, which runs after each paint. Pictures need the hook, because a picture is placed on the screen after the text is drawn. The section on pictures below explains this. The module installs the hook before the mark fix. Compositor._frame.__wrapped__ is therefore the frame without the mark fix, and the test below uses it to show the duplicated rows.

Ramabana gives shift+enter its own meaning: it starts a new line in the composer, and plain enter sends. Leela’s terminal and a default tmux never pass shift+enter on, so there it arrives as enter and sends. By default a terminal sends the same byte for both keys, so the program has to ask the terminal for richer key reports. There are two protocols for this:

  • Kitty’s keyboard protocol, with flag 1 (“disambiguate”), reports a modified key as CSI code;mods u. Ghostty and kitty support it.
  • Xterm’s modifyOtherKeys, at level 1, reports it as CSI 27;mods;code ~. Tmux sends this form when its extended-keys option is on, and the kitty form when extended-keys-format is csi-u.

The compositor asks for both, and each terminal answers with the one it supports. ext_key turns either report into the same Key the old byte parser would have produced. Once kitty’s flag is on, esc, control letters and alt letters also arrive in the new form. The decoder covers every key and follows these rules:

  • A key release is dropped.
  • Keypad keys decode to the same characters and names the old bytes gave.
  • ctrl+i, ctrl+j and ctrl+m stay tab and enter.
  • Kitty’s other private-use keys, such as bare modifiers and media keys, are dropped rather than typed.
  • Caps lock and num lock are ignored, since they are states rather than key chords.
  • Super, the command key on a Mac, adds mod+ to the name, which is Leela’s name for it, and never types a character: cmd+a decodes as mod+a.
  • Chords with hyper or meta have no names here and are dropped.

ext_keys_ok decides whether to ask. It returns True only when the compositor’s terminal and standard output are both real terminals. Tests and pipes never see the escape codes. The compositor turns the modes off wherever it hands the terminal back: at stop, at borrow when another program has the terminal, before a fatal signal, and while ctrl+z has the process suspended. A ctrl+z from the transcript view also leaves the alternate screen while suspended and returns on fg. Kitty keeps a separate flag stack for the alternate screen. The transcript view sets the flag again there and clears it before leaving.

Blocks and keys

Every block has a kind, and each kind has its own gutter, the mark in the left margin. GUTTERS maps the nine kinds to their marks: user for your prompts (▌), step for the agent’s narration (┆), tool for a tool call (│), reply for the answer, ask for an approval question (◆), plan for the plan checklist (▸), note for a message from Ramabana itself (·), error (×), and media for a picture.

A turn is one prompt and everything the agent does to answer it. In the transcript a turn reads as a timeline in the order the work happened: a step block for each stretch of narration, a tool block for each call that narration introduced, and one reply block with the answer at the end. A tool block folds to one summary row. Narration stays visible. The answer always sits below the narration that led to it.

The cell below also defines the palettes. Each palette is a dict of colour names (bg0, fg1, red and so on) to hex colours. THEMES maps each theme name to its palette. set_theme(name) selects the active palette. auto picks light or github-dark by the terminal’s background: first the terminal’s answer to the OSC11 query, then $COLORFGBG, then github-dark. Every name in THEMES is a valid cli.theme in config.toml, and is_light says which palettes draw on a light background. GRUVBOX is a legacy name that always holds the active palette, whatever its theme. code_theme, hl_theme and code_bg return the matching settings for highlighted code. plan_text draws the plan checklist in the active palette.

The key table

KEYMAP is the one list of what each key and typed command does. Each row names an action, its chords in Leela’s notation (first one first), a label, a group, the CONTEXTS it works in, and the card line of the key card it belongs to; command marks typed text such as /peers rather than keys. The key card (HELP, shown by /help and ?), the tips, the hint row’s key names and Sanketa’s keymap file are all drawn from it, so they cannot drift from each other. The key handlers keep their own code; a test checks that every chord in the table is handled and every handled chord has a row.

alt+enter queues a line for after the turn. shift+enter starts a new line in the message and never sends or queues, in terminals that report it. key_text writes a row’s keys the way the card does: a range as alt+1..9, a shared modifier once, a bare arrow as ↑.

Attachments

A prompt can carry files: pictures, sound or text. In the terminal you attach a file in one of three ways. You can drop the file on the window, paste its path, or write @path in the prompt. All three make the same attachment. The path parser accepts quoted paths, paths in brackets, file:// URIs and backslash-escaped spaces. It leaves a plain sentence that mentions a path alone. The tests below check this.

A picture goes to the model as an image content part, the form a model API takes images in. Every attachment also carries its absolute path. The path works when the model cannot take the content part. A model without audio support, for example, can open a .wav file through the file tools.

The attachment helpers themselves, media_paths, Attachment, media_parts and the rest, live in ramabana.tools and are imported here so the terminal and the other frontends share one parser.

Pictures, drawn where the terminal can draw

A picture can reach the screen in two ways. The model can return one in Resp.media. A tool can also write an image file during the turn and report it through on_media. On a terminal without kitty graphics, the picture is saved and its path is printed. kitty_graphics decides which kind of terminal this is. It reads the environment variables in KITTY_ENV and the $TERM substrings in KITTY_TERM, and it accepts the $TERM_PROGRAM names in KITTY_PROGRAM. The KITTY setting overrides all three.

On a terminal with kitty graphics the picture is drawn in place. Kitty positions an image by screen cell, separately from the text. The compositor redraws its document with absolute cursor moves. An image cannot move with the text the way prose does. A Picture handles this in two steps. Picture.send transfers the image bytes to the terminal once. The block holds only the blank rows the picture will cover. img_cells sizes them from png_size. Picture.place then writes a short placement command at the end of every frame, at the current position of those blank rows. Each placement reuses the picture’s image id and replaces the previous placement. Repaints never stack copies. Every frame places the picture again. A picture the terminal cleared comes back on the next frame.

picture builds a Picture for a file. It returns None when this terminal or this file cannot be drawn. Only .png files can be drawn. draw_png is for code that has no frames to hook into. It sends and places a picture at the cursor in one call. media_line returns the transcript line for a saved picture.

Kitty also offers Unicode placeholders, which anchor the image to special characters in the text. Ramabana does not use them. Kaku and at least one other terminal ignore the U=1 flag and draw at the cursor. They print U+10EEEE as a missing glyph and leave a block of boxes behind the picture.

The turn

A turn starts when you press enter on a prompt. run_turn runs one turn and streams it into the transcript. The agent’s stream is a blocking generator. It runs on a separate model thread, and run_turn reads its chunks from a queue. The event loop stays free to handle keystrokes, approval questions and activity updates while the model works.

Some prompts get a row of choices before the turn starts. A request such as “refactor the runtime” can mean “make the change”, “propose a plan” or “say what is in scope”. Finding out afterwards which one the model chose is costly. options_for checks the typed line against the trigger words in MENUS. It returns a title and a list of Options, or None. ChoiceMenu draws the row above the input line and handles the keys that move through it and pick one. Each Option has a suffix, an instruction that the turn appends to your prompt. The model receives the choice as part of what you asked for. REFACTOR is the only menu. The examples of the menu in use come later, under the surface.

close_done_shells closes the tmux panes of run_shell_bg commands that have finished. Their output stays readable through cmd_output.

The surface

Ui is the whole terminal surface. The rest of this page builds on it. It has three jobs. It paints the tail, the status bar and the input line at the bottom of the screen. It turns tool calls and approval requests into blocks. It decides what each keystroke means. on_key returns a coroutine for the caller to start (a turn, for example), the string 'quit', or None when the key was handled.

Every method on Ui is synchronous and does no terminal I/O of its own. The examples below drive it against an emulated terminal with no mocks. Activity and approval callbacks arrive on the model’s worker thread. Only the event loop thread may touch the compositor. _post hands those callbacks to the loop.

The class is long, and later cells add to it with fastcore’s @patch. The methods a caller uses most are submit for the typed line, say to print a block, note for a one-line message, stream for reply text as it arrives, and paint to redraw.

Shell lines

A line that starts with ! runs as a shell command in the first open folder, with no approval question, because you typed it yourself. run_shell_line runs it. Its output prints as one block, followed by the exit code, and a non-zero exit code prints as an error. The model never sees the command or its output.

So that the model knows this exists, main adds SHELL_NOTE to an interactive session’s extra_sp, the extra text appended to the agent’s briefing, before a resumed session builds its briefing. The note tells the model it can ask you to run a command with !. A one-turn run from the command line never gets the note.

The command runs in its own process group with stdin from /dev/null, so a command that tries to read from the terminal gets end of file instead of hanging. Ui.shell_proc holds the process while it runs, which is how ctrl+c reaches it (see stop further down).

mk_agent from ramabana.agent builds what the terminal runs. It makes a WorkspaceHost over the folders named on the command line, an Agent over that host, and an approval gate connected to both. A terminal that another process left non-blocking takes only part of a large frame. It then refuses the next write until it drains. AppTty waits for it and writes the rest. Only a real hangup marks the terminal gone. A gone terminal freezes the screen and quits the session on the next key:

def _drain(m, got, n):
    while sum(map(len, got)) < n: got.append(os.read(m, 1 << 16))

    os.set_blocking(s, False)
    t = object.__new__(AppTty); t.fd = s
    return m, s, t

Ui.stop

def stop():

Escalate repeated Ctrl-C from cancellation to termination to exit.

stop is what ctrl+c does, and repeated presses escalate. During a turn, the first press cancels the turn’s run, the second terminates it, and the third quits; presses count as repeats only while they come within the agent’s cancel_grace seconds of each other. Each press also takes queued lines back into the composer, so nothing you typed is lost.

For a ! command, stop signals the command’s process group. The first ctrl+c sends SIGINT, and the next sends SIGKILL, however long after the first it comes. A command ended by a signal prints stopped, and the prompt is free once the process exits. Quitting kills a command that is still running.

on_key is patched once more so that ctrl+c stops a turn without clearing the composer, and alt+up pulls queued text back into the composer for editing.

The now pane

The now pane is a small live view, in a tmux split beside the chat, of what the main agent and each sub-agent are doing at this moment: the turn, the call it is on, and each sub-agent run with its own calls.   • --pane auto|on|off decides whether a session starts with it, through start_pane; auto opens it only inside tmux.

When the viewer crashes rather than quits, the surface reopens it, a limited number of times.

Peers

Each terminal session listens on a control socket from ramabana.control, so another session can steer it, prompt it and read its events. amain starts it with start_control once the Ui exists, and closes it however the session ends. The session writes its events to EVENT_FILE in its run folder, where events reads them, and its agent gets the peers and tell tools.

UiControl keeps one owner of the turn. A peer’s prompt goes to the event loop and through start_turn, as a typed line does: it starts a turn, or it waits behind the running one in the queue and joins a line already waiting there. The transcript shows it as from a peer. A peer’s cancel is stop, which ctrl+c calls, so the lines waiting behind the turn come back to the composer and nothing is lost. status reports the Ui’s turn and queue.

The user reaches other sessions too. /peers lists them, numbered, the most recently active first, with no run ids. /tell N TEXT steers session N of that list, and /tell N --prompt TEXT starts or queues a turn there. /tell N alone aims the lines typed next at that session, as /talk does for a sub-agent, until /tell or /tell main. What the user sends this way asks for no approval, since the user typed it. A /tell whose first word is neither a number, main nor a listed session id is the agent’s own /tell RUN TEXT to a sub-agent.

Tips

While a turn runs, one grey tip: row ends the working rows. The tip is TIPS[(turn_no - 1) % len(TIPS)], so it stays for the whole turn and the next turn shows the next one. No tip shows while you type, while an approval or a menu is open, or in calm mode. tips = false under [cli] in config.toml, --no-tips or /tips off turns it off, and /tips off --save keeps that choice. Every tip names a key or command that HELP lists.

Composer controls

shift+enter starts a new line in the message and enter sends it. ctrl+a selects the whole message, and the next typed key replaces the selection. The example feeds the bytes a terminal sends: a kitty shift+enter between two words, then ctrl+a.

cm_tty = EmuTty(72, 14)
cm_comp = Compositor(cm_tty)
cm_comp._register_signals = lambda: None
await cm_comp.start()
cm_ui = Ui(cm_comp, fake_agent()[0])
cm_comp.on_key = cm_ui.on_key
cm_comp.on_bytes(b'one\x1b[13;2utwo\x01')
