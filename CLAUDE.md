# Claude instructions

Claude Code's instructions for working *on* this repository, in three layers.

- `AGENTS.md` — the harness-neutral behavioural rules, vendored from `AnswerDotAI/aai-coding`, `prompts/core.md`. Every agent reads it, Ramabana's own included: `project_context` collects it from each open root.
- `~/.claude/sysp` — the Claude-specific behavioural prompt, imported rather than copied. It is that repo's `prompts/sysp.md`, symlinked into the aai-coding checkout by its `SETUP.md`, so it is the team's shared prompt itself and not a copy of it.
- This file — what is specific to Ramabana, and nothing else.

`AGENTS.md` is byte-identical to upstream, so drift is one command:

    curl -sS https://raw.githubusercontent.com/AnswerDotAI/aai-coding/main/prompts/core.md | diff - AGENTS.md

Take an upstream change by re-fetching, never by editing the copy. A behavioural rule belongs upstream; only repository mechanics belong in this file.

`~/.claude/sysp` resolves outside the working directory, so Claude Code asks once, per project, before loading it; declining leaves it disabled without asking again. Where it does not resolve at all — a cloud container, CI, a machine without the aai-coding setup — the layers below are `AGENTS.md` and this file alone.

@AGENTS.md

@~/.claude/sysp

## Reading sysp.md in this repository

Where it names fastcore, fasthtml, nbdev and fastgit as the published libraries you shepherd, read `ramabana`: it is published, and `leela` aliases its modules, so its public APIs, defaults and behaviours are the commitments in question.

Its `<about_this_prompt>` applies literally: the import reaches the real `~/.claude/sysp`, so an edit to it is an edit to the team's shared prompt, from a session opened on an unrelated repository. Change it only when asked to, and never as part of Ramabana work.

`maturin develop` has no meaning in this checkout, so the rule against installing without approval has no exception here.

## Not the prompts the package builds

`ramabana.agent.system_prompt` assembles the briefing for agents Ramabana *runs*: `work_rules`, the skill index, the `INLINE_SKILLS` (`exhash` and `coding_patterns`) inlined in full, then `project_context`. `CLAUDE_NOTES` is that briefing's own Claude layer. None of it reads this file, and changing any of it means editing `nbs/03_agent.ipynb`.

`project_context` does read `AGENTS.md`, so the layering above is also a change to what Ramabana's agents are briefed with in this repo. The Ramabana-specific half of that briefing is `coding_patterns`, which is inlined already — which is why `AGENTS.md` can be the upstream file unchanged.

## The notebooks are the source

`nbs/*.ipynb` is the source of truth. Every module in `ramabana/` is generated and carries `# AUTOGENERATED! DO NOT EDIT!`; so are `README.md` (from `nbs/index.ipynb`), `ramabana/_modidx.py`, `ramabana/__init__.py`, and `nbs/llms.txt`. Never hand-edit a generated file — make the change in the notebook and export.

Never parse an `.ipynb` as JSON. Use `NotebookEdit`, or `fastcore.nbio` (`read_nb`, `write_nb`, `mk_cell`) in code, per `.agents/skills/nbio-notebook-edits/SKILL.md`.

The documented commands, from the Develop section of `README.md`:

    uv sync --all-extras --group dev
    uv run nbdev-export           # notebooks -> ramabana/*.py
    uv run nbdev-test             # execute every notebook
    uv run pytest                 # the plain-python suite
    uv run nbdev-clean            # before committing

Use `nbdev-prepare` (hyphen), never `nbdev_prepare`. This checkout is hatchling, so packaging changes go in `pyproject.toml` under `[tool.hatch.build]`, never `MANIFEST.in`. Installs go through `uv add`, never `pip install`. Version bumps belong to a release, never to a change.

`cd` and shell `for` loops are blocked by the safecmd allowlist here, so use absolute paths.

## Before writing code

Surface what already exists first: invoke the `kosha` skill, and `litesearch` for semantic index queries, ahead of Grep or Read. The answer is usually already in this repo or an installed package. For Python that needs state across calls, use `clikernel` rather than repeated `uv run python`; kosha and clikernel live outside the venv.

Match the surrounding design. This codebase uses fastcore selectively — `patch` to spread a class across cells, `delegates` on subclass `__init__`s, `AttrDict`, `L`, `ifnone` — but assigns in `__init__` explicitly rather than reaching for `store_attr`. Docments are the house signature style, and docstrings are one line.

Tests in `tests/` are hand-written pytest with long sentence-style names (`test_private_sections_never_reach_a_hosted_model`), plain `assert`, doubles from `ramabana.testing`, and no test loads a model. Notebooks carry the readable `test_eq` examples; `tests/` asserts contracts in bulk. Keep that division.

When something in the wider stack — fastcore, rishi, teleprint, nbdev — is missing what you need, say so rather than building around it.
