ramabana

A coding-agent harness for terminals, editors, notebooks, and MCP clients.

Ramabana runs a language model as a coding assistant. You describe a task in plain words. The model searches the code, reads and edits files, runs commands and Python, and tells you what it did. Ramabana runs that loop, decides which tools the model may call, keeps every write inside the folders you opened, and stops to ask you before anything changes.

The same agent runs in three places: a terminal session, an MCP server that lends its tools to another assistant, and your own Python program. Each of them builds the same Agent over the same tools. A behaviour in one appears in the others.

Start with one folder. Ramabana writes only inside the folders that --root names, and its reads stay inside them too unless you pass --read-outside.

How the pieces fit

A few words recur on every page of these docs.

A turn is one prompt from you and everything the agent does to answer it. During a turn Ramabana calls the model, runs the tools the model asked for, sends back their results, and calls the model again. A step is one model call and the tool calls it makes. The turn ends when the model answers without asking for a tool, or when it runs out of one of its budgets.

A tool is a Python function the model may call. Its name, arguments and docstring are what the model sees. Tools come in groups: code search, files, notebooks, the web, memory, shell commands, git, Python, and a few more. The toolset itself lives in shalya, and Ramabana imports it.

A host is the object that sets what the tools can reach: which folders they may read and write, whether the network is on, where memory is kept, and which approval gate guards a write. A host lists the groups it supports by inheriting one class per group, such as CodeHost or WebHost, and the agent offers only the tools of those groups. The terminal runs on shalya’s LocalHost. The tests run on an in-memory host from ramabana.testing.

The approval gate sits between the model and any tool with an effect, such as editing a file, running a command or making a git commit. In the default mode it asks you about each one. The Approvals section lists the other modes.

The briefing is the system prompt Ramabana writes for each session. It names the open folders, sets out how to work, lists the skills it found, and adds the project’s own instructions from files such as AGENTS.md and CLAUDE.md in each open folder.

A skill is a markdown file of guidance the agent reads only when the work calls for it. The briefing lists each skill in one line and the read_skill tool returns one in full.

A sub-agent is a second agent that the running one starts for a piece of the work, through the delegate tools. It has its own steps and transcript, works under the same approval gate, and reports back to the turn that started it.

A job is a kind of model call other than the turn itself, such as a completion, a summary or a sub-agent. Ramabana routes each job to a model suited to it, as Point it at a model explains.

Install

Ramabana needs Python 3.12 or newer. The core package holds the agent, its hosts, and the file, code, shell and git tools, which is enough to build an agent into your own program. Each extra adds one way of using it:

pip install ramabana           # the core, to build an agent or an app on
pip install 'ramabana[cli]'    # the terminal session, with search
pip install 'ramabana[all]'    # every extra
extra adds
[search] semantic code search, the vault’s memory and watches, the web tools
[serve] ramabana-mcp
[dhrona] --warm, which starts a chat with example rounds from dhrona
[cli] the terminal session, plus [search]

A program that embeds Ramabana installs only the extras it needs, such as ramabana[search,serve]. When an extra is missing, the tools that need it are left out of what the model is offered, and any command that needs it names the extra to install.

The core install already brings in the packages shalya depends on: dhrishti, jupyter-client, fossick, litesearch and vishalakshi, which in turn brings in mcp. The extras add the terminal, the MCP server and the search pieces on top.

To use the terminal on its own, run uv tool install 'ramabana[cli]' and then ramabana. The first interactive run starts inside a tmux server that belongs to Ramabana. That server needs no setup from you. It gives you the now pane, a live view of what the agent is doing in a split beside the session. It also passes the alt keys and shift+enter through to Ramabana as keys of their own. shift+enter arrives only from a terminal that sends it. Inside a tmux server of your own, Ramabana turns extended-keys on for that server when it is off. When tmux is missing, Ramabana offers the install command once. ramabana --doctor checks tmux, extended keys, the config and ramabana-pane. --tmux off or RAMABANA_TMUX=off keeps the session in the terminal you started it in. Detaching or closing the window ends the session, and --resume latest reopens it.

command what it is
ramabana the terminal session, drawn with teleprint. Needs [cli]
ramabana-mcp the MCP server. Needs [serve]
ramabana-tick one beat of the schedules, run on a timer by pobblebonk

Point it at a model

--model names the model that this session’s turns run on, called the turn model. Without it the turn model is $RAMABANA_MODEL, then $LEELA_MODEL, then [jobs] turn in config.toml, then claude-opus-5-5 through Claude Code. When that model cannot run here and neither --model nor $RAMABANA_MODEL named it, a session runs on the first model that is ready (see Set up a provider). A turn runs on this machine only when you name a local model.

ramabana --root . --model sonnet
export RAMABANA_MODEL=sonnet    # the same choice in every session
names runs on credential
opus, sonnet, fable, haiku, claude-opus-5-5, claude-sonnet-5-5, claude-fable-5-1 Claude Code a claude /login session
gpt, gpt-mini, gpt-sol, gpt-5.6, gpt-4.1, gpt-4.1-mini the OpenAI API OPENAI_API_KEY
gpt-6-luna, gpt-5.5, gpt-5.3-codex-spark Codex a Codex login
anthropic/<id> the Anthropic API ANTHROPIC_API_KEY
copilot/<id> GitHub Copilot a Copilot sign-in
azure/<deployment> Azure OpenAI, v1 API AZURE_OPENAI_ENDPOINT and AZURE_OPENAI_API_KEY
openrouter/<vendor>/<model> OpenRouter OPENROUTER_API_KEY
gemma-e2b, gemma-e4b, gemma-12b LiteRT, on the device none
qwen-4b, mini-coder-4b, ornith-9b MLX, on Apple silicon none
llama-qwen-0.6b, llama-qwen-1.7b, llama-qwen-4b llama.cpp, on the device none
ollama/<id> the ollama daemon none

/models lists what this machine can reach and marks the one running. /model NAME changes model without ending the session. /model alone prints the routing summary.

Not every model call needs the turn model. Ramabana sorts the smaller calls into jobs and sends each job to a cheaper or faster model. Completions and classification run on claude-haiku-5-5. Inline edits, summaries and other one-shot work run on gpt-6-luna through your Codex login. Delegated sub-agents run on claude-sonnet-5-5. When the turn model is local, every job without a model of its own stays on it. When a job’s default model cannot run, the job runs on the turn model and says nothing. When a model you gave a job cannot run, the job moves to another cloud route and the session says so once. A cloud model whose one-shot answer fails or comes back empty is set aside for five minutes, and its jobs move the same way. With no cloud route left, a job runs on gemma-e4b on the device, and the turn never moves. The session reports each fallback once. With nothing left at all, the error names the job, the model and the key or CLI it needs.

$RAMABANA_MODEL_<JOB> overrides one job. <JOB> is ONESHOT, INLINE, COMPLETION, CLASSIFY, SUMMARY or SUBAGENT. $RAMABANA_MODEL_IMAGE and $RAMABANA_MODEL_VIDEO set the models that generate_image and generate_video use. The turn model uses $RAMABANA_MODEL and has no _TURN variable. /model JOB NAME sets one job inside a session:

export RAMABANA_MODEL_SUBAGENT=gpt-5.6-luna

Settings for this machine

~/.config/ramabana/config.toml holds the settings you would otherwise repeat in every shell: the model for each job, the window guard’s numbers, compaction, learning, and the defaults of the terminal’s flags. Every Ramabana on the machine reads it, including one embedded in Leela (a notebook editor), another editor or an MCP client. A flag beats an env var, an env var beats the file, and the file beats the built-in default.

ramabana config init    # write the file, every key commented out beside its default
ramabana config show    # each value in effect, and whether it came from an env var, the file or the default
[jobs]
turn = "gpt-5.4"          # what $RAMABANA_MODEL and --model beat
subagent = "gpt-5.6-luna"

[window]
margin = 1.2              # charge estimated token counts 20% more

[model."openai/gpt-5.4"]  # correct a number fastllm's table has wrong
max_input_tokens = 272000

[model."claude-opus-5-5"] # a Claude Code turn silent this long is ended and tried once more
timeout = 300

Ramabana reports an entry it cannot use and applies the default. A bad entry never stops a session from starting.

ramabana config set KEY VALUE writes one key, such as subagents.effort high, runtime.tool_channel text or model."openai/gpt-5.4".tool_channel native. Quote a model name that holds a dot. ramabana config models prints the models this machine can reach, as /models does.

Tool schemas travel on one of two channels: native, the model API’s own tool field, or tags (also written text), in the system prompt. A local runtime always uses native. For every other runtime, the first of these that sets a channel decides: $RAMABANA_TOOL_CHANNEL; tags for a model whose wire refused its schemas this session; /model tools for the turn or /subagents tools for sub-agents; [model."NAME"] tool_channel; runtime.tool_channel, or for sub-agents $RAMABANA_SUBAGENT_TOOL_CHANNEL and then subagents.tool_channel; then the runtime’s default. Claude Code’s default is tags. Every other runtime’s is native. Claude Code takes native through an in-process MCP server. A managed Claude Code configuration that forbids MCP servers refuses it, and the turn goes on with tags and a note.

[subagents]
effort = "high"            # what a sub-agent asks for; $RAMABANA_SUBAGENT_EFFORT beats it
tool_channel = "native"    # how a sub-agent's tools travel; empty follows runtime.tool_channel

[model."claude-sonnet-5-5"]
tool_channel = "native"    # this model only
effort = "medium"          # when nothing else names a level

Set up a provider

A session opens whatever this machine has. When the turn’s model cannot run here, and neither --model nor $RAMABANA_MODEL named it, the session runs on the first provider that is ready, in this order: a Claude Code sign-in, a Codex sign-in, a GitHub Copilot sign-in, then an Anthropic, OpenAI or Gemini key. It never picks Azure, Bedrock or a custom endpoint, because each needs a name only you know. A job whose default model cannot run here runs on the turn model. One provider is enough. A one-shot run, ramabana 'PROMPT' or a piped prompt, with nothing ready prints the providers and exits 1.

With nothing ready, the session opens on a welcome. Inside tmux, a Getting started pane beside it lists what this machine has and what to do next, and redraws as each item is done. On WSL it says that logins, programs and variables set in Windows do not reach Linux. ramabana --doctor prints the same list.

/login                  the providers, and which are ready
/login claude           Claude Code's own sign-in, in this terminal; codex and copilot work the same way
/login openai           asks for OPENAI_API_KEY without echoing it, and keeps it in keys.env
/login bedrock          the endpoint questions, then the key
/config                 each setting in effect and where it came from
/config set KEY VALUE   writes one key and applies it to this session
/config edit            opens config.toml in $VISUAL, $EDITOR, nano or vi, and applies it on exit
/config reset           writes the commented template, keeping the old file as config.toml.bak
/model NAME --save      switches model and keeps it as [jobs] turn

A change made with /config applies to the running session. After editing config.toml by hand, /config reload applies it. A job set with /model in this session keeps its model.

~/.config/ramabana/keys.env holds the keys /login asks for. Only you can read it. Ramabana refuses a keys.env that other users can read. A variable already in the environment wins over the file. A value that starts with ! is a command, and its output is the key. A key can then stay in a password manager:

OPENAI_API_KEY=!security find-generic-password -ws openai
ANTHROPIC_API_KEY=!op read op://vault/anthropic/key

From a shell, ramabana setup asks the endpoint questions:

ramabana setup                         # pick a provider and answer its questions
ramabana setup --provider azure --model-id gpt-5.4 --endpoint https://NAME.openai.azure.com --jobs turn,summary

It writes a [model."NAME"] table into config.toml. The new model becomes [jobs] turn when config.toml names no turn and no provider is ready here. --jobs names other jobs. ramabana setup never writes a key. ramabana config show prints what is in effect.

provider needs name a model as
OpenAI API OPENAI_API_KEY gpt-5.4
Azure OpenAI AZURE_OPENAI_ENDPOINT, AZURE_OPENAI_API_KEY azure/<deployment>, or a [model."NAME"] table
AWS Bedrock AWS_BEARER_TOKEN_BEDROCK, a Bedrock API key a [model."NAME"] table on the Mantle endpoint
Anthropic API ANTHROPIC_API_KEY anthropic/<model>
Gemini API GEMINI_API_KEY gemini/<model>
OpenRouter OPENROUTER_API_KEY openrouter/<vendor>/<model>
Claude Code, Codex, Copilot a sign-in claude-opus-5-5, gpt-6-luna, copilot/<model>
any OpenAI-compatible server its URL and an env var with its key a [model."NAME"] table
this machine a local runtime gemma-e4b, qwen-4b, ollama/<model>

Azure OpenAI, by hand:

[azure]
endpoint = "https://NAME.openai.azure.com"   # or $AZURE_OPENAI_ENDPOINT; the key stays in $AZURE_OPENAI_API_KEY

[model."az-image"]                            # an Azure deployment of gpt-image-1, for generate_image
model_id = "gpt-image-1"
base_url = "https://NAME.openai.azure.com/openai/v1"

[jobs]
turn = "azure/gpt-5.4"                        # a deployment, named by its deployment name
completion = "azure/gpt-5.4-mini"
classify = "azure/gpt-5.4-mini"
image = "az-image"
video = "gemini/veo-3.0-generate-001"        # generate_video; or an Azure sora-2 [model."NAME"]

[model."azure/prod-chat"]                     # a deployment named for no known model needs its window
max_input_tokens = 200000

Requests go to https://NAME.openai.azure.com/openai/v1/responses with the deployment name as the model. No api-version is needed. A deployment named for a model, such as gpt-5.4, gets that model’s window and briefing. Any other name runs with a 128k window until max_input_tokens corrects it, and its cost reads as $0, because prices are looked up by model name.

AWS Bedrock, by hand, through its OpenAI-compatible Mantle endpoint:

[model."bedrock-gpt"]
model_id = "openai.gpt-5.4"                   # Bedrock's model id
base_url = "https://bedrock-mantle.us-east-1.api.aws/v1"
api_key_env = "AWS_BEARER_TOKEN_BEDROCK"      # a Bedrock API key; short-lived keys need renewing
api_name = "openai"                           # Responses; openai_chat for the models that offer only chat completions

[jobs]
turn = "bedrock-gpt"

Claude on Bedrock, and anything else that needs Bedrock’s native Converse API, AWS profiles or SigV4 signing, is not supported yet: fastllm, which makes the requests, implements none of them. The Mantle endpoint has no images endpoint. generate_image needs another [jobs] image.

A [model."NAME"] table with model_id defines a hosted model of any OpenAI-compatible kind under a name of your own: model_id, base_url, api_key_env (the env var, never the key), api_name (openai for Responses, openai_chat for chat completions; openai is the default on an Azure host), vendor_name, runtime and ctx. Saved model aliases live in ~/.config/ramabana/models.json (Leela keeps its own in ~/.config/leela/models.json). Every Ramabana process loads them, and config.toml’s definitions, on first use. A name defined in both places belongs to config.toml. A scheduled job, such as Dhrona’s nightly batch, sees the environment it was started with, beat.env and keys.env. A key exported only in a shell profile does not reach it.

A message too large for the window still goes out. A huge paste, a screenshot too many or a giant tool result is cut to its head and its end, the whole kept in a file under the session’s run folder, and the note in its place tells the model where the file is and to read it in pieces.

Your first session

ramabana --root .

This opens the current folder, asks before every write, and runs on the default model. Type a task and press enter. /help prints the key card and /guide the longer tour. ctrl+c stops a running turn and ctrl+d quits.

Pass a prompt instead and Ramabana runs one turn, prints the answer on stdout, and exits:

ramabana --root . 'Find where request timeouts are configured.'
ramabana --root . 'Summarise the open TODOs' > todos.md

The one-turn form prints each problem on stderr and exits 1 when the turn model was not up. A script or a git hook can test that exit code.

--root A,B . the folders it may read and write, comma separated
--model NAME routing default the model this session’s turns run on

--no-web web on takes the network away from the web tools

--pii MODE off redact or refuse for what the vault hands back, and for shell, Python and web reads a hosted model gets; cli.pii in config.toml
--pii-ner off --pii gates titled names too, not only patterns
--spec off adds api_load, api_ops and api_call
--theme NAME auto the terminal palette
--max-tool-calls N auto 20 to 400 tool calls per turn
--max-steps N auto 8 to 80 steps per turn, each a model call and its tools
--cfg DIR ~/.config/ramabana skills, extensions, history and plans
--resume ID none reopen a saved session by id, by prefix, or latest
--json off with a prompt: reply, usage, changes, activity, problems and session as JSON
--no-bell bell on no terminal bell when a turn ends or an approval waits
--no-hints hints on hides the row of keys under the status bar. hints = false in config.toml does the same
--no-tips tips on hides the tip under the working rows. tips = false in config.toml or /tips off does the same
--tmux MODE auto on or off: read the sibling panes and open the side pane. off, like RAMABANA_TMUX=off, also keeps the session out of ramabana’s own tmux
--pane MODE auto on or off: the now pane at startup. auto opens it only inside tmux

Type / and press tab to complete a command. The list holds this session’s commands, extensions included.

/root [add PATH], /theme [NAME], /mouse the open folders, the palette, and clicking blocks

/tasks, /tips [on\|off] [--save] the background shells, sub-agents and watches, and the tip shown while a turn runs

The keys:

alt+enter mid-turn, queue the line as the next turn. shift+enter does the same in a terminal that sends it

A turn reads top to bottom: ┆ narration, │ a tool call, then the answer. To send a file or an image with the prompt, drop its path on the terminal, write @path in the prompt, or use /attach PATH. tab after @ completes files and folders in the open folders, and from ~/, / or ../ when reading outside them is on. A folder attaches its listing. Quote a path with spaces: @"my notes/plan.md".

Approvals

An approval gate guards the write tools. --approve sets its mode.

mode what happens
ask every write waits for you. The default
edits file and notebook edits run; other writes wait
auto writes run unattended for the rest of the process
off the gate refuses every write
none no gate at all

At an approval prompt:

  • y approves.
  • n refuses.
  • a approves everything for the rest of the session.
  • ctrl+y approves with a note.
  • A typed reason and enter refuses with that reason.

shift+tab cycles ask, edits, auto and back to ask. From off it comes back in at ask. ctrl+g moves one step stricter, from auto to edits to ask to off, and never the other way. /approve MODE moves in either direction and answers any prompt already waiting.

The gate covers every tool with an effect:

  • files: replace_text, create_file, edit_cell, add_cell, and edit_file when --optin exhash offers it
  • code: run_python, run_shell, run_shell_bg
  • git: git_commit, git_checkout, git_stash, git_remote, git_sync, git_conflicts
  • the rest: memory_forget, create_skill, cancel_watch, add_root

Git goes through those tools. Merge or rebase with git_sync, not run_shell. Settle conflicts with git_conflicts, and git_status shows the plan. run_shell refuses git commit|push|pull|fetch|stash|switch|checkout|merge|rebase and names the tool to use. Ramabana snapshots every git write so /rewind can undo it. When the same gated call comes three times running, Ramabana asks you rather than run or refuse it again, whatever the mode.

The folders it can touch

--root is the file policy. Name every folder, comma separated:

ramabana --root .,~/notes,/srv/app

Writes reach those folders and nowhere else. Reads start out in the same folders. --read-outside widens reads to any path on the machine and leaves writes where they were. /root prints the open folders, and /root add PATH opens another mid-session for reading and writing.

Sub-agents, started through the delegate tools, may write, run commands and run Python by default. Every write remains behind this session’s approvals. --no-subagent-writes or /subagents off restricts them to read-only tools. A read-only session refuses delegate_async(writes=True). delegate_search hands its sub-agents read tools only unless the model passes writes=True. Several read-only questions then run at once.

A sub-agent runs on the subagent job’s model, claude-sonnet-5-5 by default. /subagents model NAME changes it for this session, and /subagents model default goes back to config.toml’s. The model may also name a model per delegation: delegate_search(questions, model=...) takes one name for every question or a list with one per question. A named model that is unknown or not set up here fails that question with the setup message, and no other model answers in its place. Read-only questions on different cloud models run at once. Questions on the session’s local engine run one after another. Writes run one at a time.

effort is low, medium, high, xhigh or max. A delegation’s own effort comes first, then /subagents effort, then $RAMABANA_SUBAGENT_EFFORT, then config.toml’s [subagents] effort, then the model’s default. Claude Code takes the level as its effort. A hosted model takes it as its reasoning effort. OpenAI and Azure take max as xhigh. A local model takes no effort level. It runs at its default and the answer says so. A provider that refuses the level is asked once more without it, and the answer says so. Sub-agents do not take the turn’s own reasoning level.

A sub-agent takes at most 80 steps and runs for at most 1800 seconds by default. /subagents steps N and /subagents timeout S change those limits. timeout 0 removes the time limit. A delegation’s max_steps stays within the session cap and has a floor of 20 steps unless the session cap is lower. Two levels of sub-agents may delegate again by default. /subagents nest 0 disables nesting. A nested sub-agent gets only delegate_search. The sub-agents under one turn share one tool-call budget the size of the turn’s own. At most four run at once.

Every run keeps a transcript under <cfg>/runs/<session>/. Inside tmux:

  • /watch RUN opens a pane that tails the transcript.
  • /watch monitors tails the folder reviews.
  • /tell RUN TEXT sends a running sub-agent a message. It gets the message with its next tool result.
  • read_terminal reads the sibling panes.
  • run_shell_bg logs to a file rather than opening a pane. The side pane’s Background rows show its output, and p on one follows it in a tmux pane.

/pane opens the now pane in a split on the right. It shows the turn, the call it is on, and each sub-agent run with its own calls. The split needs tmux 3.1 or later, and --pane on opens it at startup. Without tmux, or with --tmux off, /pane prints the ramabana-pane command to run in another terminal instead.

Budgets, cost and history

A turn runs until the model stops calling tools. --max-tool-calls caps the tool calls. --max-steps caps the steps, each one model call and the tools it runs. Both take auto or a number: 20 to 400 calls, 8 to 80 steps. /tool-budget and /steps change them mid-session and print what the last turn ran under.

/cost prints:

  • the tokens in and out
  • the cached share
  • the reasoning tokens
  • the spend, when the backend reports one

/compact summarises the history so far and carries on with the shorter context. /compact NOTE tells the compactor what to keep.

Ramabana saves every session with a completed turn under --cfg, which defaults to ~/.config/ramabana. /sessions lists them with their turn counts and models. /resume ID reopens one from a full id or a unique prefix. From the shell:

ramabana --root . --resume latest

A resumed session brings back its history and its plan. It prints on stderr any other folder that session had open, and /root add PATH opens it again.

Memory, API specifications and a beat

--vault keeps what the agent reads in a vishalakshi vault, for the next session to retrieve. --pii redact masks personal data on the way back out of the vault, and in the shell, Python and web reads sent to a hosted model; file reads keep it, because edits match text exactly. --pii refuse refuses those reads instead. API keys and tokens are masked as [SECRET] in every read whatever --pii says, and commands that print the environment are refused. --pii-ner extends either mode to titled names, not only patterns. Either mode needs --vault. Without it the command exits 2 and does not ignore the flag; a cli.pii in config.toml is skipped instead.

--spec adds api_load, api_ops and api_call. Point api_load at an OpenAPI, Azure or Google Discovery document and the agent can call the operations it describes.

Some work should happen on a timer even when no session is open. A schedule is a callback that pobblebonk fires at set times. A package registers one under the ramabana.ticks entry point, as dhrona does, and Python code registers one with ramabana.monitor.on_tick(name). A beat is one pass that runs every schedule that has come due. ramabana-tick runs one beat and leaves what the schedules found as notes, which the next session reads. --install registers the command with cron, launchd or schtasks. Beats then run while no session is open:

ramabana-tick --install --every 300    # a beat every five minutes
ramabana-tick                          # one beat now
ramabana-tick --uninstall

Skills and extensions

A skill is markdown the agent reads when the work calls for it. Ramabana looks for skills in these folders, in order:

  • <cfg>/learned/skills
  • <cfg>/skills
  • ~/.agents/skills
  • .leela/skills and .agents/skills under each open folder

When two skills share a name, the later folder wins. In each folder, a skill is a subfolder holding a SKILL.md. Five skills ship inside the package as Python modules: coding_patterns, debugging, theory, write_prose and write_docs. Any folder above overrides them. /skills lists what this session found, and /skill NAME prints one.

<cfg>/learned holds what dhrona, a separate package that learns from past sessions, kept from earlier sessions. Its skills override the packaged ones and lose to every folder you write. Its AGENTS.md goes in the briefing after Ramabana’s own rules and before the project instructions, and the project instructions outrank it. A learned skill is listed like any other and read when a task needs it. A learned skill that replaces an inlined skill is clipped in the briefing to the same cap as AGENTS.md. No proposal from dhrona reaches a session until you accept it. Each proposal waits on a pending/ branch of the folder’s own git repository. /learned in a session, or ramabana-learned from a shell, lists them, and diff ID, accept ID and reject ID act on one. Ramabana refuses an accept that would take AGENTS.md past the 2,000 characters dhrona allows. /learned compact ID then asks dhrona to merge and shorten the paragraphs it wrote, with that proposal folded in. Your own paragraphs stay as they are. The shorter file waits for review like any proposal. Accepting a proposal moves the other proposals onto it, and a proposal that no longer applies is marked stale. ramabana.learned offers the same to a host. --no-learned starts a session without the folder. /learned off, or ramabana-learned off, sets learning = false in config.toml and turns learning off for every session on this machine. Nothing learned is briefed, no lessons are kept or read, and the nightly batch does nothing until /learned on.

An extension adds behaviour without changing Ramabana. It is a Python file in <cfg>/extensions with a setup(reg) function, and through reg it can:

  • add a tool
  • add a slash command
  • register a skill
  • hook the turn
  • replace the approval policy
def setup(reg):
    @reg.tool
    def deploy_status() -> str:
        "What is deployed right now."
        return open('/var/run/deploy').read()

    reg.command('deploys', lambda agent, arg: deploy_status(), help='what is deployed')
    reg.on('after_tool', lambda agent, name, out: print(name, file=open('/tmp/tools.log', 'a')))

The hook events are before_turn(agent, prompt), after_turn(agent, text), before_tool(agent, name, args), after_tool(agent, name, out), compact(agent, text) and approval. reg.approval(fn) replaces the approval policy, and the last registration wins. /extensions prints one line per extension: loaded, or why not. /reload loads skills, extensions and tools again after an edit.

Talk between sessions

Claude Code, Codex and Ramabana sessions on one Mac can send each other messages. A note shares news. An ask requests work. A reply returns the result with proof.

Set up the hooks once. This step edits the Claude Code hook settings and gives the session the peer-work skill:

ramabana setup peers --agent claude

Plain ramabana setup does not install these hooks. The command shows the diff of ~/.claude/settings.json and asks before it writes. Add --yes to write without the question. Use --agent codex for Codex, or --agent all for both. --remove takes the hooks out again.

A Claude Code session registers when it starts. A session that was already running before the setup does not appear in ramabana peers. Restart it, or resume it with claude --resume. ramabana --doctor shows whether each agent has the hooks.

List the live sessions:

ramabana peers

Send a note to a session. Add --ask to request work, and --wait 120 to wait for the reply:

ramabana tell sanketa "The Card API moved to v2"
ramabana tell --ask --wait 120 sanketa "Add a Card part"

Work together mode lets the named sessions send you asks without a question to the user. Each session keeps its own permission mode. The mode ends at the set time, after 12 hours if you set no time, or with ramabana together off. In a Claude Code or Codex session it also ends when you type. In a Ramabana session, /together on starts it, and so does telling the agent to work with peers: the agent calls its work_together tool. In auto permission mode the tool runs without a question; ask and edits ask you. A turn that a peer message reached cannot call it:

ramabana together on --with abhyasa,leela --until 07:00

A thread carries at most 6 messages: the ask and 5 replies. Each session sends at most 40 notes and asks in 12 hours; replies do not count. So two sessions cannot loop all night. When the mode ends, Ramabana saves a morning report. It lists each thread, its changes, its proof and the actions left for you:

ramabana report

Serve the tools to another assistant

ramabana-mcp serves one host’s tools over MCP:

ramabana-mcp --root .

By default the server mounts only the read tools, because the client cannot reach this process’s approval gate. --write mounts the write tools too. --model NAME adds one further tool, ask, which runs a whole Ramabana turn and returns only its answer. --model also builds the agent. The mounted tools are then the same objects a turn gets, and they record into the same activity log. The server offers skills as resources rather than tools: an index, plus one per skill. A client lists them and fetches the one it needs.

option default what it does
--root A,B . the folders to serve
--model NAME none adds the ask tool, running on this model
--write off mount the write tools too
--no-web web on takes the network away from the web tools
--read-outside off reads may name any path. Writes stay inside
--vault, --pii MODE, --pii-ner off as in the terminal
--transport NAME stdio stdio, sse or streamable-http
--cfg DIR none skills and extensions, with --model

A model-less server still finds skills in the served folders and in ~/.agents/skills. The server loads --cfg and its extensions only when --model builds the agent.

A client that launches its own servers takes the command:

{"mcpServers": {"ramabana": {"command": "ramabana-mcp", "args": ["--root", "/srv/app"]}}}

Drive it from Python

ramabana.agent.mk_agent builds what the terminal runs: a host over the folders you name, and an Agent whose approval gate works the way approve says. agent.ask(prompt) runs one turn and returns the answer.

The example below goes through the same Agent.ask path with fake_agent from ramabana.testing. Instead of a real model it uses a backend that returns the replies you give it, and instead of your disk it uses a small in-memory project. It needs no credentials or downloads and writes nothing.

A long-running program, such as a web app that runs agent jobs, uses the same calls with these options:

  • Read roots: mk_agent(read_roots=[...]) opens folders that the read tools search and no write touches. The system prompt names them.
  • Many asks: an ask is one approval request waiting for an answer. Approvals holds every waiting ask. answer(id, ok) resolves any of them, and waiting lists them oldest first. Each ask appears through on_activity as an awaiting row with its ask_id before its call runs.
  • A policy: Approvals(policy=fn) is consulted before rules and modes. fn(name, args) returns 'allow', 'deny', 'ask' or None.
  • Waiting and timeouts: no_listener='wait' holds an ask until a page listens, and that page is shown the asks already waiting. on_timeout='allow' lets an unanswered ask through, except one that the policy or the loop guard put to a person.
  • A typed result: agent.ask(prompt, schema=Model) returns a TurnResult whose result is a validated Model.
  • Sessions: Agent(session_id=...) names the session. A turn in a session another live process holds raises SessionBusy.
  • Budgets: max_cost, max_tokens, session_max_cost and session_max_tokens stop a turn that passes them. The turn is recorded with state budget.
  • An event file: agent.events_to(path) writes one JSON line per call, ask, plan change, turn start and end, and steering delivered. A file past max_bytes rolls over to <name>.1.
  • A queue: agent.queue(prompt) holds a prompt, and agent.run_queued() runs what is held, in order. Steering a turn never read joins the next turn.
  • A full resume: resume_session(id, full=True) restores the conversation as its last turn left it, every tool result whole. A stop that leaves a backend running hands its conversation to the next one.
  • Defaults for a host: mk_agent(python='off') withholds Python. mk_agent(global_skills=False) leaves ~/.agents/skills out. rules_path= names the job’s own rules file. Agent(extra_sp=...) adds to the briefing.
  • A worktree: host.add_worktree(repo, branch) makes a git worktree for the job and opens it as a root.
  • A control socket: ramabana.control.Control(agent).start() listens on a socket in the session’s run folder, and control_call(path, method, ...) prompts, steers, cancels and answers it from another process, and takes messages from peer sessions.

examples/embed_host.py runs one such job end to end.

from ramabana.testing import fake_agent

agent, backend = fake_agent(replies=['The threshold is defined in `pkg/sizes.py`.'])
answer = agent.ask('Where is the threshold defined?')
answer
'The threshold is defined in `pkg/sizes.py`.'
assert agent.history[-1]['prompt'] == 'Where is the threshold defined?'

agent.turn_lines(), repr(agent.turn_use)
(['🔍 Search Where is the threshold defined?'],
 '15 tok · in 10 · out 5 · model')

Read the implementation

Start with the page for the contract you need:

  • core: errors, routing, model budgets, and shared values
  • models: the model catalog, curated and discovered
  • runtime: backends, usage, runs, and compaction
  • tools: hosts, tool construction, and delegation
  • agent: turns, approvals, activity, plans, history, and branching
  • testing: in-memory hosts and deterministic backends
  • terminal and MCP: frontend adapters, the now pane beside the terminal, and the first-run setup that starts it in tmux
  • vault, API specifications, and folder monitoring: optional capabilities
  • control: a local socket a detached job runner listens on
  • learned: the review queue for what Dhrona proposes for the learned folder
  • coding patterns, debugging, theory, prose, and documentation: bundled agent skills

The toolset itself is shalya, the git plumbing is gheasy, and the scheduler is pobblebonk.
