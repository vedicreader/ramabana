The Agent class: one conversation with a model, the tools it may call, the approvals that guard them, and the record of what it did.

The activity feed

The activity feed is the list of tool calls a turn has made, one row per call. A frontend draws each row as a short human line, such as View a.py:4-, rather than a raw view_file(path='a.py', start=4). Each tool carries its own summary function for that line, and summarise from tools calls it. The cell below shows the line for five common tools.

tool = {t.__name__: t for t in tools_for(FullHost())}
[summarise(tool[t], a) for t, a in [
    ('search_code', {'query': 'where is compaction triggered'}),
    ('view_file', {'path': 'nbs/01_runtime.ipynb', 'start': 40, 'end': 80}),
    ('edit_cell', {'path': 'nbs/00_core.ipynb', 'cell_id': '451586c0'}),
    ('inspect_python', {'code': 'list(df.columns)', 'scope': 'overlay'}),
    ('git_status', {}),
]]

A tool without a summary function, such as one an extension added, still gets a line: its name and arguments, as the last example shows. Every tool the toolset ships has a summary, which the bare check asserts.

test_eq(summarise(tool['view_file'], {'path': 'a.py', 'start': 4}), 'View a.py:4-')
test_eq(summarise(tool['view_file'], {'path': 'a.py', 'end': 8}), 'View a.py:-8')
test_eq(summarise('view_file', {'path': 'a.py'}), 'View a.py')
bare = sorted(t.__name__ for t in tools_for(FullHost()) if getattr(t, 'summary', None) is None)
test_eq(bare, [])
summarise('word_count', {'path': '/proj/a.py'})

Approvals

A write tool is one that changes something: it edits a file, runs a command, or commits to git. The approval gate stands between the model and those tools. Before a write runs, the gate raises an Ask, a request a person answers yes or no, shows a preview of what the call would do, and waits. A refusal goes back to the model as the tool’s result, with the person’s reason, so the model can change its approach.

The gate’s mode decides who answers:

mode what happens
ask every write waits for a person
edits file and notebook edits run; other writes wait
auto every write runs
off every write is refused

edits never covers the ALWAYS_ASK tools (add_root, restart_kernel, page_eval); they still wait for a person. A session built with approve='none' has no gate at all.

Approvals is the gate itself. It holds every request still waiting (waiting lists them oldest first, and pending is the oldest), tells the frontends that listen, and blocks the model’s thread until each request is answered, refused or timed out. Each call gets its own decision, so a model that asks for four writes gets four requests. Its main parameters are:

  • tools, the names that need approval; an agent adds every write tool it builds;
  • mode, one of the four modes above;
  • timeout, the seconds a request waits (DFLT_TIMEOUT, 300), or None to wait forever;
  • policy, a host’s function fn(name, args) returning 'allow', 'deny', 'ask' or None, consulted before saved rules and the mode;
  • rules_path, a JSON file of saved allow and deny rules, which always adds to;
  • no_listener and on_timeout, what happens when no frontend listens or nobody answers in time.

The examples below walk through each case.

A request with no frontend listening is refused at once, and the reason says so. Waiting would hold the model’s thread for the whole timeout, for an answer that cannot come. no_listener='wait' holds the request until a frontend calls listen instead.

listen registers a frontend. Its on_ask callback receives each new Ask, and the frontend answers with answer(ask.id, ok, note). Here the callback answers at once; a real interface shows the preview and answers when the person decides. listen returns a function that unregisters the frontend.

bool(decision), decision.reply()

In auto mode every write is approved without asking, and a plain approval has no note, so its reply is None. In off mode every write is refused, with a reason that names the mode.

A model that makes the same gated call three times in a row is stuck. The same call means the same tool with the same arguments, with no other gated call in between. auto mode would let it carry on, and ask mode would put the same question a third time. Instead the DOOM_LOOPth repeat, the third, goes to a person as a forced ask, whatever the mode.

  • It takes the ordinary request path, so the terminal waits and a frontend is asked again.
  • With nobody listening, it is refused, and the reason names the loop.
  • off mode and a saved deny rule still answer first.
  • A different call starts the count again.
spin = Approvals(tools={'edit_file'}, mode='auto', timeout=1)
asked = []
spin.listen(on_ask=lambda a: (asked.append(a), spin.answer(a.id, False, 'stop looping')))
call = {'function': {'name': 'edit_file', 'arguments': {'path': 'a.py'}}}
test_eq([bool(spin.gate(call)) for _ in range(3)], [True, True, False])
test_eq(len(asked), 1)
assert asked[0].preview.startswith('the same call three times running')
test_eq(bool(spin.gate({'function': {'name': 'edit_file', 'arguments': {'path': 'b.py'}}})), True)
alone = Approvals(tools={'edit_file'}, mode='auto')
[alone.gate(call) for _ in range(2)]
alone.gate(call).reply()

A request nobody answers within timeout is refused, and the reason gives the wait. on_timeout='allow' lets it through instead, except for a request the policy or the loop guard put to a person. When a turn is cancelled, cancel_all refuses what is waiting, so no worker thread is left blocked.

slow = Approvals(tools=WRITE_TOOLS, timeout=0.01)
slow.listen(on_ask=lambda a: None)
slow.request('edit_file', {'path': 'a.py'}).reply()

timeout=None waits as long as it takes. mk_agent passes None by default, which suits the terminal, where a person sits at the screen. Approvals itself, and the ACP server, keep DFLT_TIMEOUT.

patient = Approvals(tools=WRITE_TOOLS, timeout=None)
patient.listen(on_ask=lambda a: threading.Timer(0.05, patient.answer, (a.id, True)).start())
test_eq(bool(patient.request('edit_file', {'path': 'a.py'})), True)
test_eq(Approvals().timeout, DFLT_TIMEOUT)
test_eq(DFLT_TIMEOUT, 300)

Tools the user names

The model chooses its own tools during a turn. A person can also name one in the prompt: /search_code compaction threshold asks for search_code with that query. prompt_directives finds such names, and the turn adds them to its plan. The briefing

The briefing is the system prompt: the standing instructions the model reads with every turn. system_prompt builds it from these parts, in order:

  1. what the agent is, and the folders it may work in;
  2. a description of this machine, when the host gives one;
  3. the working rules (work_rules), keeping only those whose tool is offered;
  4. the skill catalogue, each skill’s name and the first sentence of its description;
  5. any skill inlined whole;
  6. lessons kept in <cfg>/learned/AGENTS.md;
  7. the project’s own instructions (project_context);
  8. extra, text the caller adds last.

A skill is a markdown document that tells the model how to do one kind of work. The catalogue lists names only, and the model calls read_skill for a body when it needs one, because a dozen full skills would crowd out the code the model has to read. The one exception is INLINE_SKILLS: exhash is inlined, and inline_for keeps it only when edit_file, the tool it teaches, is offered.

The session plan

The session plan is the checklist the model keeps of what it is doing: a title and a list of todos, each pending, active, done or cancelled, with at most one active. It is saved beside the history, so it survives a stopped turn and a restart. While it has steps it appears in every briefing, so after a stop the model continues from the active item. It lives on the Agent rather than the host, so the terminal, the MCP server and Leela all read the same object.

Plan holds the list and Todo is one step. Plan.update changes a step found by id, unique id prefix or unique text, and marking one step active moves any other active step back to pending.

The agent

One Agent holds one continuous model conversation. Building one is cheap: no model loads until the first turn. Attached to it are:

  • routing, which model each job runs on (see core);
  • tools, skills and extensions;
  • the approval gate and compaction;
  • the activity feed, the plan and the history on disk.

A job is one kind of model work. turn is the main conversation; oneshot, inline, completion, classify, summary and subagent are short jobs that can run on other, cheaper models. A missing model is reported, never raised. The model may be a download of several gigabytes or need an API key, and an editor should still open without either; ready and note say whether the turn model is up, and why not.

The main constructor options:

  • approvals, an Approvals gate, or None for no gate;
  • cfg, the config folder for history, plans, skills and extensions; None keeps nothing on disk;
  • subagent_writes, on by default: sub-agents get write tools, behind the same gate;
  • readonly, which withholds every tool that acts;
  • max_cost, max_tokens, session_max_cost and session_max_tokens, budgets that stop a turn;
  • keep_conversation, which saves the whole conversation each turn for a full resume;
  • profile, auto, small or full, described below.

Git writes go through git tools, never the shell. When the session offers the git tool, run_shell refuses the seven subcommands that have one (commit, push, pull, fetch, stash, switch, checkout) and names the tool to use. git_shell_denial finds them wherever they appear:

  • anywhere in a &&, ; or | chain, split after quoting, so a quoted git commit inside an echo is only text;
  • after any NAME=value prefix, or a git option such as -C;
  • behind one env, xargs, nohup, time, command, exec or nice wrapper, or inside a sh -c "..." line.

gheasy’s classify decides what counts as a read, so git stash list runs and git stash is refused. A git tool returns an undo token, and the agent keeps it so /rewind can undo the write.

_guard applies this rule and two more before any call runs. A shell line may not hide its own output with | head, | tail or 2>&1 (shell_denial), and a write may not hand-edit a module nbdev generated from a notebook (generated_denial).

Before a message goes out, _fit makes it fit the turn model’s window, cheapest step first, and stops at the first that fits:

  1. A message, or a newest exchange, larger than half the room the briefing leaves is cut to an excerpt first, so a short conversation is not compacted to make room for one paste. A prompt holding a <notebook> is left to the notebook step.
  2. The oldest tool results, then the oldest pictures, are trimmed (Backend.trim).
  3. The conversation is compacted, whether or not compaction.auto is on.
  4. The notebook’s discard and then auto cells are left out (compact_notebook_context).
  5. The newest two messages are cut (Backend.shrink_recent).
  6. The message itself is cut to the room left (fit_content): the newest pictures that fit stay, and text becomes its head and its end around a note naming the file that holds it whole. The reminders _prepare added to its end are kept whole.

Whatever is cut is written whole under <runs_dir>/full, readable by this user alone, and the note says how to read it with the tools the model has: view_file(path, start=N) in pieces, or grep. When the read tools cannot reach that folder, it is opened to them for reading only. The log keeps the prompt as it was typed.

Inline completion

Inline completion suggests the next few lines of code at the cursor, as an editor does. It returns at most four lines, has to feel instant, and is worth little per call, so it runs on the completion job’s model in a throwaway conversation. It runs only when asked for, never on every keystroke: the kernel’s own completions are instant and correct, while this costs a model call.

_clean makes a raw reply safe to insert. Asked for bare code, a completion model often wraps it in a fence, repeats the line it continues, and writes past the point where it can guess. _clean takes the code out of the fence, drops the repeated text, and keeps at most max_lines lines.

Once a run is cancelled, any tool call it attempts is not started, and returns a note saying so.

Cancelling a streamed turn stops it at once. The stream ends with what had arrived, the run leaves the active list, and the turn is recorded with state cancelled. The turn is not finished, so no check runs and no checkpoint is saved. on_registered is called with the run before any output, so a host can keep its id; a cancel there means the model is never called.

class _BlockingBackend(FakeBackend):
    def __init__(self):
        super().__init__(replies=['unused'])
        self.first, self.release, self.cancelled = threading.Event(), threading.Event(), False
    def stream(self, msg, run=None, **kw):

Assembly

mk_agent is the one call that builds a working session: a WorkspaceHost over the named folders, an Approvals gate in the mode approve names (none builds no gate), and an Agent on both. The terminal and the MCP server start here, and so can any application that runs agent jobs. mk_host builds just the host, with the web, vault, API-specification and PII options.

Pass cfg= for history, skills and saved approval rules, read_roots= for folders to search but never write, python='off' to withhold Python, and any other Agent option by keyword. The agent starts without a code index; host_kw controls it. The index shows a session driven from Python.
