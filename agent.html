The Agent class: one conversation with a model, the tools it may call, the approvals that guard them, and the record of what it did.

The activity feed

The activity feed is the list of tool calls a turn has made, one row per call. A frontend draws each row as a short line such as View a.py:4-, not as a raw view_file(path='a.py', start=4). Each tool has a summary function that makes this line. summarise from tools calls it. The cell below shows the line for five common tools.

tool = {t.__name__: t for t in tools_for(FullHost())}
[summarise(tool[t], a) for t, a in [
    ('search_code', {'query': 'where is compaction triggered'}),
    ('view_file', {'path': 'nbs/01_runtime.ipynb', 'start': 40, 'end': 80}),
    ('edit_cell', {'path': 'nbs/00_core.ipynb', 'cell_id': '451586c0'}),
    ('inspect_python', {'code': 'list(df.columns)', 'scope': 'overlay'}),
    ('git_status', {}),
]]

A tool without a summary function, such as one an extension added, still gets a line. The line is the tool name and its arguments, as the last example shows. Every tool in FullHost has a summary, and the bare check asserts this.

bare = sorted(t.__name__ for t in tools_for(FullHost()) if getattr(t, 'summary', None) is None)
test_eq(bare, [])
summarise('word_count', {'path': '/proj/a.py'})

Act is one row of the feed. It is one tool call, and it exists from the moment the call starts. A frontend can show ⏳ Web fetch: ... while the fetch is still running. kind comes from the tool’s group and selects the icon. line returns the one-line text.

Activity is the whole feed for a session. It calls on_change when a row starts and when it finishes, which is twice per call. A frontend redraws from this callback. rows returns the feed as dicts, lines returns one string per call, and md returns folded markdown. The feed keeps at most max_acts rows (MAX_ACTS, 500) and drops the oldest first.

Approvals

A write tool is a tool that changes something: it edits a file, runs a command, or commits to git. The approval gate stands between the model and these tools. Before a write runs, the gate raises an Ask. An Ask is a request that a person answers with yes or no. The gate shows a preview of what the call would do and waits. A refusal goes back to the model as the tool result, with the person’s reason. The model can then change its approach.

The gate’s mode decides who answers:

mode what happens
ask every write waits for a person
edits file and notebook edits run; other writes wait
auto every write runs
off every write is refused

edits mode does not cover the ALWAYS_ASK tools (add_root, restart_kernel, page_eval). These tools still wait for a person in edits mode. In off mode they are refused. A session built with approve='none' has no gate.

def preview_for(

What this call would do, as text a person can read quickly.

A backend hands the approver each tool call as a dict in the OpenAI shape, {'function': {'name': ..., 'arguments': ...}}, where the arguments may be a JSON string. _tc returns the name and the parsed arguments.

_tc({'function': {'name': 'edit_file', 'arguments': '{"path": "a.py", "commands": "[]"}'}})

preview_for turns one call into the text a person reads before approving it. The useful preview depends on the tool: the edit commands for edit_file, a diff for replace_text and edit_cell when the host can read the file, the head of the new file for create_file (and whether it overwrites one), and the command line for run_shell.

print(preview_for('edit_file', {'path': 'a.py', 'commands': [['2|ab12|', 's', 'return 1', 'return 2']]}))
h = MemHost({'/proj/a.py': 'x = 1\n'})
p = preview_for('replace_text', {'path': '/proj/a.py', 'edits': [{'oldText': 'x = 1', 'newText': 'x = 2'}]}, h)
assert '-x = 1' in p and '+x = 2' in p, p
assert 'old' in preview_for('edit_cell', {'path': '/proj/n.ipynb', 'cell_id': 'c1', 'edits': [{'oldText': 'old', 'newText': 'new'}]})
assert '12|ab| s' in preview_for('edit_file', {'path': 'a.py', 'commands': [['12|ab|', 's', 'old', 'new']]})
assert 'a.py' in preview_for('replace_text', {'path': '/proj/a.py', 'edits': 'not json'}, h)
print(preview_for('create_file', {'path': 'new.py', 'text': 'def f(): pass\n'}, host=NullHost(['/proj'])))

Approvals is the gate itself. It holds every request that is still waiting. waiting lists them oldest first, and pending is the oldest. The gate calls the frontends that listen. It blocks the model’s thread until each request is answered, refused or timed out. Each call gets its own decision. A model that asks for four writes causes four requests. The main parameters are:

  • tools, the names that need approval; an agent adds every write tool it builds;
  • mode, one of the four modes above;
  • timeout, the seconds a request waits (DFLT_TIMEOUT, 300), or None to wait forever;
  • policy, a host’s function fn(name, args) returning 'allow', 'deny', 'ask' or None, consulted before saved rules and the mode;
  • rules_path, a JSON file of saved allow and deny rules, which always adds to;
  • no_listener and on_timeout, what happens when no frontend listens or nobody answers in time.

A request with no frontend listening is refused at once, and the reason says so. Without this, the model’s thread would wait for the whole timeout for an answer that cannot come. With no_listener='wait' the request waits until a frontend calls listen.

gate = Approvals(tools=WRITE_TOOLS)
gate.listeners, gate.request('edit_file', {'path': 'a.py'}).reply()

listen registers a frontend. Its on_ask callback receives each new Ask. The frontend answers with answer(ask.id, ok, note). Here the callback answers at once. A real interface shows the preview and answers when the person decides. listen returns a function that unregisters the frontend.

stop = gate.listen(on_ask=lambda a: gate.answer(a.id, False, 'rewrite it as a patch instead'))
decision = gate.request('edit_file', {'path': 'a.py', 'commands': '[]'})
bool(decision), decision.reply()

A tool outside tools is approved at once, and no frontend sees a request. The Ask is still recorded in history.

test_eq(gate.pending, None)
len(gate.history)

In auto mode every write is approved without asking. A plain approval has no note, and its reply is None. In off mode every write is refused, and the reason names the mode.

Approvals(tools=WRITE_TOOLS, mode='auto').request('edit_file', {}).reply(), Approvals(tools=WRITE_TOOLS, mode='off').request('edit_file', {}).reply()

answer(..., session=True) approves the request and switches the gate’s mode for the rest of the session. The new mode is auto unless scope names another. When the person gave no note, the gate adds a note that records the change.

stop()

first = gate.request('edit_file', {'path': 'a.py'})
gate.mode, first.note
test_eq(gate.mode, 'auto')

A model that makes the same gated call three times in a row is stuck. The same call means the same tool with the same arguments, with no other gated call in between. auto mode would let the model continue, and ask mode would put the same question a third time. Instead the DOOM_LOOPth identical call, the third, goes to a person as a forced ask in ask, edits and auto mode.

  • It takes the ordinary request path. The terminal waits for the person, and a frontend is asked again.
  • With nobody listening, it is refused, and the reason names the loop.
  • off mode and a saved deny rule still answer first.
  • A different call starts the count again.
spin = Approvals(tools={'edit_file'}, mode='auto', timeout=1)
asked = []
spin.listen(on_ask=lambda a: (asked.append(a), spin.answer(a.id, False, 'stop looping')))
call = {'function': {'name': 'edit_file', 'arguments': {'path': 'a.py'}}}
test_eq([bool(spin.gate(call)) for _ in range(3)], [True, True, False])
test_eq(len(asked), 1)
test_eq(bool(spin.gate({'function': {'name': 'edit_file', 'arguments': {'path': 'b.py'}}})), True)
alone = Approvals(tools={'edit_file'}, mode='auto')
[alone.gate(call) for _ in range(2)]
alone.gate(call).reply()

A request nobody answers within timeout is refused, and the reason gives the wait. With on_timeout='allow' the request is approved instead. A request that the policy or the loop guard put to a person is still refused. When a turn is cancelled, cancel_all refuses every waiting request. No thread stays blocked.

slow = Approvals(tools=WRITE_TOOLS, timeout=0.01)
slow.listen(on_ask=lambda a: None)
slow.request('edit_file', {'path': 'a.py'}).reply()

Tools the user names

The model chooses its own tools during a turn. A person can also name a tool in the prompt. /search_code compaction threshold requests search_code with that query. prompt_directives finds such names, and the turn adds them to its plan. The briefing

The briefing is the system prompt: the standing instructions the model reads with every turn. system_prompt builds it from these parts, in order:

  1. what the agent is, and the folders it may work in;
  2. a description of this machine, when the host gives one;
  3. the working rules (work_rules), keeping only those whose tool is offered;
  4. the skill catalogue: each skill’s name and the first sentence of its description, clipped to CATALOGUE_CHARS (70) characters;
  5. any skill inlined whole (a skill from the learned folder is clipped to MAX_CONTEXT_FILE);
  6. lessons kept in <cfg>/learned/AGENTS.md;
  7. the project’s own instructions (project_context);
  8. extra, text the caller adds last.

A skill is a markdown document that tells the model how to do one kind of work. The catalogue lists names only. The model calls read_skill to get a body. The one exception is INLINE_SKILLS. exhash is inlined. inline_for keeps it when edit_file, the tool it teaches, is offered, or when no tool list is given.

small_system_prompt is the short briefing for small local models. It holds the folders, one line about the machine, SMALL_RULES, and clipped lessons and project instructions.

The session plan

The session plan is the checklist the model keeps of what it is doing: a title and a list of todos, each pending, active, done or cancelled, with at most one active. It is saved beside the history, so it survives a stopped turn and a restart. While it has todos it appears in every briefing, so after a stop the model continues from the active item. It lives on the Agent rather than the host, so the terminal, the MCP server and Leela (a notebook editor) all read the same object.

Plan holds the list and Todo is one item of that list. Plan.update changes a todo found by id, unique id prefix or unique text, and marking one todo active moves any other active todo back to pending.

The agent

One Agent holds one continuous model conversation. Building one is cheap, and no model loads until the first turn. An agent also holds:

  • routing, which model each job runs on (see core);
  • tools, skills and extensions;
  • the approval gate and compaction;
  • the activity feed, the plan and the history on disk.

A job is one kind of model work. turn is the main conversation; oneshot, inline, completion, classify, summary and subagent are short jobs that can run on other, cheaper models. A missing model is reported, not raised. The model may be a download of several gigabytes or need an API key. An editor must still open without either. ready and note say whether the turn model is up, and why not.

The main constructor options:

  • approvals, an Approvals gate, or None for no gate;
  • cfg, the config folder for history, plans, skills and extensions; None keeps nothing on disk;
  • subagent_writes, on by default: sub-agents get write tools, behind the same gate;
  • readonly, which withholds every tool that acts;
  • max_cost, max_tokens, session_max_cost and session_max_tokens, budgets that stop a turn;
  • keep_conversation, which saves the whole conversation each turn for a full resume;
  • profile: auto, small or full, described below.

Git writes go through git tools, never the shell. When the session offers the git tool, run_shell refuses the seven subcommands that have one (commit, push, pull, fetch, stash, switch, checkout) and names the tool to use. git_shell_denial finds them in each of these places:

  • anywhere in a &&, ; or | chain, split after quoting. A quoted git commit inside an echo is only text;
  • after any NAME=value prefix, or a git option such as -C;
  • behind one env, xargs, nohup, time, command, exec or nice wrapper, or inside a sh -c "..." line.

gheasy’s classify decides what counts as a read. git stash list runs, and git stash is refused. A git tool returns an undo token. The agent keeps the token, and /rewind uses it to undo the write.

_guard applies this rule and three more before any call runs. shell_denial refuses a shell line that hides its own output with | head, | tail or 2>&1, and, through env_denial, a line that prints environment values, which is where API keys live: printenv in any form, env with no command to run, a bare set or export, export -p, declare -x or declare -p, any read of /proc/*/environ, and cat, less, more, head, tail, grep, tac, nl or strings of a .env file (not of a template such as .env.example). It looks through sudo, nice, timeout, xargs and the like, through $( ) and sh -c. The refusal tells the model to ask whether one variable is set instead. It is a best-effort first layer: backticks, eval, a script that prints os.environ and many other routes get past it, and the read guard below, which masks key shapes in whatever a command prints, is what stops a key whatever the route. generated_denial refuses a write that hand-edits a module nbdev generated from a notebook, and secret_denial refuses a write that would put the [SECRET] mask over a real key. shell_denial applies to run_shell and run_shell_bg. The git rule applies to run_shell only.

Before a message goes out, _fit makes it fit the turn model’s window, cheapest step first. It stops at the first step after which the message fits:

  1. A message, or a newest exchange, larger than half the room the briefing leaves is cut to an excerpt first. A short conversation is not compacted to make room for one paste. A prompt holding a <notebook> is left to the notebook step.

  3. The conversation is compacted, whether or not compaction.auto is on.
  4. The notebook’s discard and then auto cells are left out (compact_notebook_context).

Inline completion

Inline completion suggests the next few lines of code at the cursor, as an editor does. It returns at most four lines. It has to feel instant, and each call is worth little. It runs on the completion job’s model in a throwaway conversation. It runs only when asked for, never on every keystroke. The kernel’s own completions are instant and correct, and this costs a model call.

_clean makes a raw reply safe to insert. Asked for bare code, a completion model often wraps it in a fence, repeats the line it continues, and writes past the point where it can guess. _clean takes the code out of the fence, drops the repeated text, and keeps at most max_lines lines.

What a read may send

Every tool result goes to the model, and for a hosted model that means to another company’s servers. mk_host gives the host a read_guard built by masking_guard, and shalya asks it about every read the tools make: files, notebook cells, search hits, diffs, web pages, shell output and Python output. The guard answers with the text to send instead, or a refusal.

Secrets are masked in every read, always, whatever --pii says, by mask_secrets (its shapes are listed with the shell rules above). A key is found by its prefix on a word boundary, so one glued to a word character, such as XSK_sk_live_…, is not; a key with no fixed prefix, such as an AWS secret access key or a Hetzner token, is never found, and the shell rules and the file tools’ refusal of credential paths are what keep those out.

Personal data is masked only where --pii asks, which needs --vault, and only in shell, Python, URL and page reads sent to a hosted model, that is, when ReadCheck.local is false or unknown. With redact the guard masks rahasya’s personal-data kinds; with refuse it withholds a read that holds any. Code reads (view_file, view_cell, grep, diffs) get their secrets masked and nothing else, because the agent edits files by exact text: an email address masked in a file it reads would make every oldText around it match nothing. A local model sees personal data as it is. A key masked in a file can still break an edit whose oldText spans it; that edit fails and says so, and is the price of never sending the key. secret_denial stops the worse case, a write tool putting [SECRET] back over the key; a shell or Python write such as sed -i is not checked.

Assembly

mk_agent is the one call that builds a working session: a WorkspaceHost over the named folders, an Approvals gate in the mode approve names (none builds no gate), and an Agent on both. The terminal and the MCP server start here, and so can any application that runs agent jobs. mk_host builds just the host, with the web, vault, API-specification and PII options, and gives it masking_guard as its read_guard unless the caller passes one.

Pass cfg= for history, skills and saved approval rules, read_roots= for folders to search but never write, python='off' to withhold Python, and any other Agent option by keyword. The agent starts without a code index; host_kw controls it. The index shows a session driven from Python.

def mk_agent(
    roots:tuple=('.',), model:NoneType=None, approve:str='ask', # ask | edits | auto | off | none (no gate)
    web:bool=True, # wire the web tools to fossick
    vault:bool=False, # keep reads in a vishalakshi vault
    spec:bool=False, # let the agent load OpenAPI/Azure/GCP specs
    read_outside:bool=False, # read-only tools may name any path
    pii:str='off', # off | redact | refuse PII from the vault, and from shell, Python and web reads a hosted model gets
    pii_ner:bool=False, # gate titled names too, not only patterns
    host_kw:NoneType=None, # to `mk_host`: `index` (off: `sync_index` runs it after the model), `warm`, `vault=<path>`
    read_roots:tuple=(), # folders the read tools search and no write touches
    python:str='host', # 'host' runs `run_python` in this process, 'off' withholds it
    rules_path:NoneType=None, # saved allow/deny rules; None shares `<cfg>/approvals.json` with every session on that cfg
    timeout:NoneType=None, # seconds an ask waits for an answer; None waits forever
    no_listener:str='refuse', # an ask with nobody listening: 'refuse', or 'wait' for a listener
    on_timeout:str='refuse', # an ask nobody answers in time: 'refuse' or 'allow'
    **kw
):

A host over roots and an Agent on it, gated as approve says; no code index until asked.
